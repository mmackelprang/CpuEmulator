## 1. Context

ADR 0005 decided the 8086's **state, segmentation, bus, and flags** — and found them to be a near-total reuse of the M4 substrate. This ADR decides how the 8086 is **decoded and addressed**, scopes its **instruction set**, lays out the **M5 PR arc**, recons the **8088 TomHarte vectors**, and records the **M4.5a gate-scoping lesson** as binding guidance.

The post-M4 decode substrate (verified file:symbol against the live tree on the in-flight M4.5 branch — read-only):

- **Two decode front-ends exist, both feeding one back-end.** `EmitStructuredDecodeWalk` (`src/CpuEmulator.Generators/CpuEmitter.cs:3997`) emits the **byte-granular** walk (6502 degenerate + Z80 prefix/compound + a *synthetic* ModR/M + sub-field path); `EmitFieldDecodeWalk` (`CpuEmitter.cs:4106`) emits the **word-granular** 68000 field-decode walk. The selector is `if (model.FieldGrammar is { } grammar && grammar.FetchUnit == FetchUnit.Word)` (`CpuEmitter.cs:4003`) — a declared word `FieldGrammar` routes to the field walk; everything else falls to the byte walk. Both return one `DecodeResult(key, computed-length, operands)` (`Jit/IDecoder.cs:27`) consumed by the interpreter `Step`, the JIT `Discover`, the disassembler, and `InstructionLength` alike.
- **The fetch stream is unit-granular and already names the 8086.** `IFetchStream` (`Jit/IDecoder.cs:7`) carries `UnitBytes` (1 byte or 2 word), `NextUnit()`, `PeekUnit()`, `UnitsConsumed`; its doc-comment literally reads "Default unit = byte (6502/Z80/**8086**)." The byte-granular 8086 will use `UnitBytes = 1` over an `AddressSpaceFetchStream`/`BusFetchStream` (the existing byte streams).
- **The byte walk's ModR/M path is a SYNTHETIC PLACEHOLDER, not real x86.** In `EmitStructuredDecodeWalk` (`CpuEmitter.cs:4067–4073`): `s_modRmOpcodes.Contains(first)` reads one ModR/M byte and consumes `tail = modrm & 0x03` more bytes — a **proof-of-shape** for "a mid-stream byte determines length," explicitly documented as "the synthetic CPU's proof." `LengthRule.ModRmDetermined` (`Jit/OpcodeDescriptor.cs:56`) is documented "length = base + f(the next consumed byte) — **the synthetic/8086 case**." **No live CPU declares `ModRmOpcodes`** (the Z80 declares only `Prefixes`). The `& 0x03` is NOT the real x86 ModR/M length math; it is a placeholder the synthetic-CPU test exercises. `DecodeStructure` (`Specification/DecodeStructure.cs:9`) carries `byte[] ModRmOpcodes` + `byte[] SubFieldOpcodes`, described as built for "Z80 prefixes, **8086 ModR/M**."
- **The byte walk has NO prefix-STACKING and NO operand-determined immediate length.** The Z80 prefix path handles *one* prefix (or one compound `DD CB` pair, `CpuEmitter.cs:4041`); it does not model **0–4 stacked prefixes** (segment-override + `REP`/`REPNE` + `LOCK` + operand/address-size — though the last two are 80386, see scope). The degenerate `LengthRule.Fixed` path consumes a per-mode **constant** (`OpcodeDescriptor.FixedLength`, `OpcodeDescriptor.cs:66`); there is **no path where the opcode byte + the ModR/M byte + the displacement size + the immediate size jointly determine a variable length from the front of a byte stream**.
- **The EA descriptor pattern exists (68000) but is `M68k`-named.** `EmitM68kEa` (`CpuEmitter.cs:4270`) emits `ComputeEa(eaMode, eaReg, size, ExtensionWords ext, bool pureEa)` (`CpuEmitter.cs:4274`); `M68kEaLegality.IsLegal(mode, reg, category)` (`SpecParser.cs:1746`); the displacement helper `EmitZ80IndexedEa(sb, indexReg, dispExpr)` (`CpuEmitter.cs:2209`, `base + (sbyte)disp`) is the base+signed-displacement seam both Z80 and 68000 reuse. **Structurally generic, named per-CPU** — the 8086 builds its own analogue.
- **The importer has two disjoint arms.** `OpcodeDataset.Parse` (`tools/CpuEmulator.SpecImporter/OpcodeDataset.cs:148`) keys on single-byte hex (`OpcodeEntry`, with optional Z80 prefix-plane) → `SpecImportEngine.RunFromFiles`; `FieldGrammarDataset.Parse` (`tools/CpuEmulator.SpecImporter/FieldGrammarDataset.cs:49`) parses the 68000's `FieldGrammarFamily` 8-tuple → `SpecImportEngine.RunFieldGrammarFromFiles`. The selector is `--field-grammar` vs `--dataset` in `Program.cs:89`. Generated specs land **per-CPU** (`src/CpuEmulator.Cpus.M68000/M68000Spec.cs`, etc.), guarded by `M68000RegeneratedSpecTests.Committed_M68000Spec_is_exactly_the_tool_output`.

This ADR's organizing question: **does the byte-granular decode front-end (the 6502/Z80 path + its synthetic ModR/M placeholder) extend to the real 8086 variable-length prefix-stacking decode, or does the 8086 need a distinct decode front-end feeding the same back-end?** The answer is the load-bearing M5 finding (Decision 1).

## 2. Decisions

### Decision 1 (LOAD-BEARING) — The 8086 needs a NEW byte-granular variable-length decode front-end (a third `Emit…DecodeWalk` arm), NOT an extension of the existing prefix/synthetic-ModR/M byte walk; it reuses the back-end (opaque key, computed length, `DecodeResult`, descriptor resolution) unchanged

**The substrate-gap question, answered.** The existing byte walk (`EmitStructuredDecodeWalk`) gives the 8086 **the shape but not the substance**:

- ✅ **Reusable, unchanged:** the fetch abstraction (`IFetchStream` byte mode, `UnitBytes = 1`); the **opaque-key + computed-length contract** (`DecodeResult(key, length, operands)`, length = `UnitsConsumed × UnitBytes`, never a field read — `CpuEmitter.cs:4086`); the **descriptor-by-key dictionary** (`DescriptorFor`, the keyed table the 68000 also uses for its `(operation,size)` key); the `JitOpClass`/`LengthRule` enums; the whole interpreter/JIT/disassembler back-end that consumes a `DecodeResult`. The 8086 produces a `DecodeResult` exactly like the 68000 does — only the *walk that produces it* differs.
- ❌ **NOT reusable — the 8086 forces a new walk:** the existing byte walk models (a) **one** prefix or one compound pair, not **0–4 stacked prefixes** (segment-override `26/2E/36/3E`, `LOCK` `F0`, `REP`/`REPNE` `F3`/`F2`); (b) a **synthetic** ModR/M length (`modrm & 0x03`, `CpuEmitter.cs:4072`) that is **not** the real x86 ModR/M-byte addressing-mode length table; (c) **no** operand-size-and-immediate-determined length (the real 8086 length is `prefixes + opcode(1) + [ModR/M(1)] + [disp(0/1/2)] + [imm(0/1/2)]`, where the disp size comes from the ModR/M `mod` field and the imm size comes from the opcode + the `w`/`s` bits — a genuine multi-input computation from the front of the stream). The `& 3` placeholder cannot express this; forcing the real math through it would misrepresent the encoding (the same trap ADR 0004 Decision 1(B) rejected for the 68000 — "the `SubField` carrier was built for the 8086 ModR/M shape, not field-decomposition," and conversely the synthetic ModR/M placeholder was built for the *shape* proof, not real x86 length).

**Options.**

- **(A) A new `EmitX86DecodeWalk` arm, selected by a new declared decode-structure variant (byte fetch unit + a `Prefixes`-stacking + ModR/M-length-table + immediate-length declaration), emitting the real x86 length computation; reuse the entire back-end (key dictionary, `DecodeResult`, descriptor resolution).** The walk: consume 0–4 known prefix bytes (accumulating segment-override + repeat + lock state); consume the opcode byte (possibly a `0F` two-byte escape — *deferred*, see scope); if the opcode has a ModR/M operand, consume the ModR/M byte and compute the **displacement length from `mod`+`r/m`** (the real 8086 16-bit table: `mod=00`+`r/m=110` ⇒ disp16; `mod=01` ⇒ disp8; `mod=10` ⇒ disp16; `mod=11` ⇒ register, no disp); consume the **immediate** whose length the opcode + `w`/`s` bits dictate; the key is the opcode byte (plus the ModR/M `reg` field for opcode-group instructions like the `80`/`81`/`F6`/`FF` groups — analogous to the existing `SubFieldOpcodes` `(first<<3)|((next>>3)&7)` keying, `CpuEmitter.cs:4065`, which *is* reusable for the group case); the length is `UnitsConsumed`.
  - *Pros:* this is **the same architecture as the 68000's third arm** — `EmitFieldDecodeWalk` was added beside `EmitStructuredDecodeWalk` rather than contorting the byte walk into word-granularity; the 8086 adds `EmitX86DecodeWalk` beside both, selected by a declared variant, **reusing the back-end the same way**. It matches the real silicon length math (so the TomHarte length/transaction trace is right). The prefix-stacking, the ModR/M length table, and the immediate length become **generator code in one place**, not scattered. The opcode-group keying reuses the existing sub-field key shape. The 6502/Z80/68000 walks are **untouched** (the new arm is opt-in via the variant selector, exactly as `FetchUnit.Word` is).
  - *Cons:* a genuinely new decode-walk emitter (the largest of the three, because x86 length is the most input-dependent: prefixes × ModR/M × `w`/`s` × opcode-group). It is **real generator work**, the highest-risk M5 abstraction (the 68000's field walk was the highest-risk M4 abstraction — symmetric). The risk is under-scoping it as "the synthetic ModR/M path, finished" — the *shape* (mid-stream-byte-determines-length) is there, but the *substance* (the real x86 length table + prefix stacking + immediate sizing) is entirely new.
- **(B) Finish the existing synthetic ModR/M path into real x86 (replace `modrm & 0x03` with the real table; add prefix stacking to the Z80 prefix path).**
  - *Pros:* fewer new symbols; reuses `EmitStructuredDecodeWalk` literally.
  - *Cons:* **rejected.** It would entangle the 8086's real length math with the Z80's prefix/compound logic in one method (`EmitStructuredDecodeWalk` already handles prefix + compound + sub-field + synthetic-ModR/M + degenerate in one walk — adding real x86 on top makes it a five-CPU-shaped megamethod). The 68000 deliberately got its *own* arm rather than overloading the byte walk; the 8086's variable-length decode is *more* divergent from the Z80 prefix model than the 68000's word decode was, not less. Overloading the shared byte walk risks an accidental cross-arm behavior change to the Z80 (a `RegeneratedSpec`-guarded regression). Keep the arms separate.
- **(C) A flat 256-entry (× ModR/M) table.**
  - *Cons:* **rejected** (the perennial flat-table option, ADR 0001 Decision 1(C) / ADR 0004 Decision 1(C)) — the 8086 length depends on prefixes + ModR/M + immediates, not on the opcode byte alone; a flat table cannot carry it.

**Decision: (A) — a new `EmitX86DecodeWalk` arm, selected by a new byte-granular variable-length decode-structure variant, reusing the back-end unchanged.** The substrate-gap headline: **the FieldGrammar/field-decode model does NOT extend to the 8086 (it is word-granular and 68000-specific); the existing byte walk gives the 8086 only the *shape* of mid-stream length, not the real x86 substance; so the 8086 gets a third decode front-end — but it feeds the *same* opaque-key/computed-length/`DecodeResult` back-end the other two arms feed.** This is the direct analogue of how the 68000 got `EmitFieldDecodeWalk` beside `EmitStructuredDecodeWalk`.

Concretely:
- A new declared variant (a sibling to `DecodeStructure`/`FieldGrammar`, e.g. an `X86DecodeStructure` carrying: the prefix byte set + their roles (segment-override/repeat/lock); the opcode → has-ModR/M map; the opcode-group set (the `reg`-field-extends-opcode rows); the immediate-length rule per opcode (`w`/`s`-bit driven)). Absent ⇒ the existing byte walk (6502/Z80) or field walk (68000) — **byte-identical**.
- `EmitX86DecodeWalk`: stack prefixes → opcode → optional ModR/M (real 16-bit `mod`/`r/m` disp-length table) → immediate → key = opcode (or `(opcode<<3)|reg` for groups, reusing the sub-field key shape) → length = `UnitsConsumed`. The **ModR/M byte's `mod`/`reg`/`r/m` fields are carried as operands** on the `DecodeResult` (the EA descriptor, Decision 2/3) — exactly as the 68000 carries its `(eaMode, eaReg)` + `ExtensionWords`. The accumulated **segment-override** is threaded to the EA layer (ADR 0005 Decision 2); the **repeat prefix** is threaded to the string-op body.

**Consequences.**
- *Good:* the 8086 reuses the *entire* decode back-end (the most-tested part); the new arm is the *front* only, isolated and opt-in; the 6502/Z80/68000 walks are untouched (no `RegeneratedSpec` risk); the opcode-group keying reuses the existing sub-field key. This **validates the multi-front-end-one-back-end architecture** the 68000 introduced — a third decode shape proves it generalizes.
- *Bad:* `EmitX86DecodeWalk` is the highest-risk M5 abstraction (the most input-dependent length math of the three CPUs). **Mitigation (the M4.3a/M3.1b discipline): ship the SHAPE + a synthetic variable-length-decode fixture proving prefix-stacking + ModR/M-disp-length + immediate-length BEFORE the 8086 dataset depends on it** (the same "prove the variant against a synthetic fixture first" rule the field walk followed). The synthetic ModR/M placeholder (`modrm & 0x03`) is **retired/superseded** by the real arm — but note it is currently only exercised by a synthetic-CPU test, so retiring it touches no shipped CPU (verify the synthetic-CPU test is migrated or kept as the degenerate proof).

### Decision 2 — ModR/M decode: the `mod:reg:r/m` byte → a structured EA descriptor (16-bit 8086 EA modes); `reg` is register-or-opcode-extension per the opcode; reuse the EA-descriptor PATTERN (not the 68000's `ComputeEa`)

**The problem.** The 8086 ModR/M byte packs three fields: `mod`(7-6) `reg`(5-3) `r/m`(2-0). The `reg` field is **either a register operand OR an opcode extension** (the `80`/`81`/`83`/`F6`/`F7`/`FE`/`FF`/`D0`–`D3`/`C0`/`C1`(80186)/`8F` groups, where `reg` selects which of eight operations — `ADD`/`OR`/`ADC`/… for the `80`-group). The `mod`+`r/m` pair selects one of the **16-bit effective-address forms** (the 8086 has a small fixed EA table, NOT the 68000's 14 modes):

| `mod` | `r/m` | EA |
|---|---|---|
| 00 | 000–111 (except 110) | `[BX+SI]`, `[BX+DI]`, `[BP+SI]`, `[BP+DI]`, `[SI]`, `[DI]`, **`[BP]`→ but `mod=00,r/m=110` is `disp16` direct**, `[BX]` |
| 00 | 110 | `disp16` (direct address) — the exception |
| 01 | as above | same base+index **+ disp8** (sign-extended) |
| 10 | as above | same base+index **+ disp16** |
| 11 | 000–111 | register direct (`AX`/`CX`/… or `AL`/`CL`/… per the `w` bit) |

The default segment per EA (ADR 0005 Decision 2): forms using `BP` default to `SS`; the rest default to `DS`; a segment-override prefix replaces it.

**Decision: a structured 8086 EA descriptor — `(mod, reg, r/m, dispLen, disp, segOverride)` — built by `EmitX86DecodeWalk`, consumed by a new `EmitX86Ea`/segment-resolution EA layer (ADR 0005 Decision 2), reusing the 68000's EA-descriptor PATTERN and the `EmitZ80IndexedEa` displacement-helper SEAM — but NOT the 68000's `ComputeEa` itself (which is 14-Motorola-mode-shaped with `(An)+`/`-(An)` write-back + `ExtensionWords`).** Concretely:
- The ModR/M-derived **offset** is computed by an 8086 EA helper: a small `switch` on `(mod, r/m)` producing `base(BX/BP/none) + index(SI/DI/none) + disp(0/8/16)`, **wrapped at 16 bits** (ADR 0005 Decision 2 quirk), then handed to the segment-resolution step (`(seg<<4)+offset`). The base+index+disp addition reuses the **base+signed-displacement pattern** of `EmitZ80IndexedEa` (`CpuEmitter.cs:2209`), the same seam the 68000 reused for `d16(An)`/`d8(An,Xn)`.
- The **`reg` field's role is opcode-determined**: for a register-operand opcode it names a register (`w`-bit selects 8/16-bit, e.g. `reg=000,w=1`⇒`AX`, `w=0`⇒`AL`); for an opcode-group opcode it **extends the opcode** (and is folded into the decode key by the group key shape, Decision 1). This dual role is data on the opcode descriptor (a `regIsExtension` flag per opcode), not a code branch.
- **No EA write-back side effect** — the 8086 has no `(An)+`/`-(An)` analogue (string ops step `SI`/`DI`, but that is a *string-op-body* concern driven by `DF`, not an EA-descriptor side effect — keep it in the string-op body, not the EA layer). So the 68000's `pureEa`/write-back machinery is **not needed**; the 8086 EA is pure-functional (compute offset, no architectural mutation), which is *simpler* than the 68000's EA.

**Consequences.**
- *Good:* the EA-descriptor *pattern* (mode/register/displacement as operands on the `DecodeResult`, a `switch`-driven compute) is the proven 68000 shape; the displacement-addition seam (`EmitZ80IndexedEa`) is reused a third time; the 8086 EA is *simpler* than the 68000's (no write-back, a small fixed table vs 14 modes). The opcode-group `reg`-extension reuses the sub-field key shape. **No new `AddrMode`/`JitMode` enum member** (`AddrMode.cs` / `Jit/OpcodeDescriptor.cs:20`) — the 68000 set the precedent of carrying EA in a structured descriptor, not enum members, killing the mirror-table tax (ADR 0004 Decision 2); the 8086 follows.
- *Bad:* a net-new `EmitX86Ea` + the 8086 EA table + the `mod=00,r/m=110`⇒`disp16` exception + the 16-bit-wrap + the `BP`⇒`SS`-default rule — the correctness surface (TomHarte-caught). The `reg`-as-register-vs-extension dual role must be data-driven per opcode (a mis-set flag is a wrong-decode bug).

### Decision 3 — The importer: a new x86 dataset arm (opcode-table + ModR/M/group/immediate metadata), a third disjoint importer arm; the 8088 TomHarte loader reuses the gzip/mnemonic-keyed loader PATTERN

**The problem.** The 6502/Z80 use the single-byte-hex `OpcodeDataset` arm; the 68000 uses the `FieldGrammarDataset` field-pattern arm. The 8086 is **opcode-table-shaped** (like the 6502/Z80 — a primary opcode byte per instruction) **but with per-opcode metadata the existing `OpcodeEntry` does not carry**: has-ModR/M, `reg`-is-opcode-extension (+ the group's eight operations), the immediate-length rule (`w`/`s`-bit driven), the default-segment, the prefix roles.

**Decision: a third disjoint importer arm — an x86 opcode-table dataset (`OpcodeEntry`-like rows + the ModR/M/group/immediate/prefix metadata) → a new `SpecImportEngine.RunX86…` path, selected by a new `--x86` (or `--opcode-table-x86`) flag in `Program.cs`.** It is **closer to the 6502/Z80 opcode-row arm than to the 68000 field-grammar arm** (a primary-opcode-keyed table, not a bit-field grammar) — but it carries the new x86 metadata the byte-hex arm lacks, and it drives the new `EmitX86DecodeWalk`. The pipeline law holds (dataset → importer → generator → `M8086Spec.cs` under `src/CpuEmulator.Cpus.M8086/`, guarded by an `M8086RegeneratedSpecTests` byte-identity test, mirroring `M68000RegeneratedSpecTests`).

The **8088 TomHarte loader reuses the M4.4b gzip/mnemonic-keyed pattern** (Decision 5 confirms the schema). It is a *parameterization-plus* of `M68000TomHarteLoader` (`tests/.../TomHarte/M68000TomHarteCase.cs:50`) — same gzip decompression, same mnemonic-keyed file iteration, a different per-case state schema (8086 registers + queue, not 68000 `d`/`a`/`usp`/`ssp`/`prefetch`) and a different transaction tuple. Recommend a `M8086TomHarteVectors`/`M8086TomHarteCase` pair beside the 68000 one, the cache resolver `<cache>/8088/v2` (Decision 5), and a `[M8086TomHarteTheory]` skip-when-absent attribute (mirroring `M68000TomHarteTheoryAttribute`, `M68000TomHarteVectors.cs:32`).

**Consequences.**
- *Good:* the importer's disjoint-arm pattern (`Program.cs:89` selector) cleanly accepts a third arm; the regen byte-identity guard pattern carries over; the TomHarte loader is a known-shape parameterization, not net-new infrastructure (the gzip/mnemonic mechanics are proven). The x86 dataset is opcode-table-shaped (familiar) with declarative metadata.
- *Bad:* a third dataset schema + a third importer arm + a third regen test + a fourth TomHarte loader variant — real but bounded importer work (each follows an established pattern). The x86 opcode-table dataset is large (~256 primary opcodes + the group sub-tables + the prefixes); building it accurately (the has-ModR/M / immediate-length / default-segment per opcode) is the dataset's correctness burden, cross-checked against a second x86 reference per the extraction-as-acceptance-test discipline (ADR 0001 Decision 6).

### Decision 4 — Instruction-set scope for v1: the real-mode 8086 integer ISA, family-by-family; defer the genuinely-later families

**Decision.** v1 = the **8086 real-mode integer instruction set**, scoped family-by-family (mirroring M4.5's MOVE→ALU→shift/bit→control split). **In scope for v1:**

- **Data movement:** `MOV` (all forms: reg/reg, reg/mem, mem/reg, imm/reg, imm/mem, to/from segment registers, `MOV AL,[addr]`/accumulator-direct), `XCHG`, `LEA`, `LDS`/`LES`, `PUSH`/`POP` (reg/mem/segment), `PUSHF`/`POPF`, `LAHF`/`SAHF`, `XLAT`, `IN`/`OUT` (the port bus — note: the 8086 has a separate **I/O space** via `IN`/`OUT`, the `JitOpClass.Port` / `IoPort*` modes already exist from the Z80, `OpcodeDescriptor.cs:13` — reuse them; this is the one place the 8086 has a second bus, like the Z80's I/O space).
- **Arithmetic:** `ADD`/`ADC`/`SUB`/`SBB`/`CMP`/`INC`/`DEC`/`NEG`, `MUL`/`IMUL`/`DIV`/`IDIV`, the BCD adjust ops `AAA`/`AAS`/`AAM`/`AAD`/`DAA`/`DAS`.
- **Logic/shift/rotate:** `AND`/`OR`/`XOR`/`NOT`/`TEST`, `SHL`/`SAL`/`SHR`/`SAR`, `ROL`/`ROR`/`RCL`/`RCR` (the 8086 forms: by 1 or by `CL`).
- **Control flow:** `JMP` (short/near/far, direct/indirect), the conditional `Jcc` family (`JZ`/`JNZ`/`JC`/`JNC`/`JO`/`JS`/`JP`/`JBE`/`JLE`/… and synonyms), `LOOP`/`LOOPE`/`LOOPNE`/`JCXZ`, `CALL`/`RET` (near/far), `INT n`/`INT3`/`INTO`/`IRET`.
- **String ops:** `MOVS`/`CMPS`/`SCAS`/`LODS`/`STOS` (byte+word), the `REP`/`REPE`/`REPNE` prefix (the `CX`-counted repeat — analogous to the Z80 block ops `LDIR`/`CPIR`, ADR 0001 J9, a one-instruction loop driven by `CX` + the `DF` step direction).
- **Flag/processor control:** `CLC`/`STC`/`CMC`/`CLD`/`STD`/`CLI`/`STI`, `NOP`, `HLT` (reuse the generic `Halted` member, the Z80 `HALT`/68000 `STOP` precedent), `WAIT`/`LOCK`/`ESC` (decode + no-op-or-fallback semantics for v1).

**Deferred (out of v1, explicit):**
- **The `0F` two-byte opcode escape** and all 80186/80286/80386+ instructions (`ENTER`/`LEAVE`/`BOUND`/`PUSHA`/`POPA`/`IMUL imm`/`SHL imm`/the `0F` plane) — the SingleStepTests 8088 set is *8088* (Decision 5), so the v1 gate does not require them; decode them as illegal/fallback for now.
- **Protected mode, the descriptor tables, paging** — not an 8086 concern (80286+).
- **The full cycle-accurate timing axis** (the per-transaction trace cycle counts, the 6-byte 8088 prefetch/instruction-queue state) — sequenced into a **late** sub-milestone (Decision 6, the lesson-learned).

**Family-by-family interpreter split (mirroring M4.5a–d):**
- **M5.5a — `MOV` + the EA pipeline** (all MOV forms incl. segment-register moves + accumulator-direct; proves the decode→ModR/M→EA→segment→bus pipeline end-to-end, the way M4.5a MOVE proved the 68000 pipeline). Pulls forward whatever decode-length completeness the first real ModR/M rows force.
- **M5.5b — integer ALU** (`ADD`/`ADC`/`SUB`/`SBB`/`CMP`/`INC`/`DEC`/`NEG`/`TEST`/`AND`/`OR`/`XOR`/`NOT`, `MUL`/`IMUL`/`DIV`/`IDIV`, the BCD adjusts) — the flag-setting core (CF/PF/AF/ZF/SF/OF correctness, the parity + aux-carry subtleties, ADR 0005 Decision 3).
- **M5.5c — shift/rotate + stack + misc** (`SHL`/`SHR`/`SAR`/`ROL`/`ROR`/`RCL`/`RCR`, `PUSH`/`POP`/`PUSHF`/`POPF`/`LAHF`/`SAHF`, `XCHG`/`XLAT`/`LEA`/`LDS`/`LES`, the flag-control ops, `NOP`/`HLT`).
- **M5.5d — control flow + strings + interrupts** (`JMP`/`Jcc`/`LOOP`/`JCXZ`/`CALL`/`RET`, `INT`/`IRET`/`INTO`, the string ops + `REP`, `IN`/`OUT`, the interrupt seam + vector table + `IF`/`TF` machinery — and **here** the timing/prefetch-queue axis is introduced, per Decision 6).

**Consequences.**
- *Good:* a coherent, gated v1 (the full real-mode 8086 integer ISA, matching the 8088 vector coverage) with a clean family-by-family split that mirrors the proven M4.5 cadence; `IN`/`OUT` reuse the existing Z80 I/O-bus seam; `REP` reuses the Z80-block-op precedent; `HLT` reuses the generic `Halted`. The deferrals are principled (the gate doesn't need `0F`/186+).
- *Bad:* the BCD adjusts (`AAM`/`AAD`/`DAA`/`DAS`) + the flag subtleties + the string-op `REP`/`DF` interaction are the dense correctness pockets (TomHarte-caught); the ISA is large (more primary opcodes than the 68000's family count). Bounded by the family split.

### Decision 5 — TomHarte 8088 vector recon (read-only, as far as determinable)

**Determined read-only (the repo + the M4.4b pattern):**
- **Source repo:** `SingleStepTests/8088` (GitHub) — the 8088 ProcessorTests set, the "v2" generation referenced for x86. (The 6502 lives in `SingleStepTests/ProcessorTests`/`6502/v1`; the Z80 in `SingleStepTests/z80`; the 68000 in `SingleStepTests/680x0`/`68000/v1`. The 8088 is its own `SingleStepTests/8088` repo.) **No 8086/8088 fetch script exists yet** in `tools/` (verified — only `get-test-vectors.ps1`, `…-z80.ps1`, `…-68000.ps1`, `get-klaus.ps1`, `get-zexall.ps1`). A future fetch PR adds `tools/get-test-vectors-8088.ps1` following the **68000 temp-clone+sparse-checkout+move pattern** (`tools/get-test-vectors-68000.ps1`): clone `SingleStepTests/8088` shallow+sparse, check out the vector subtree, move into `<cache>/8088/v2`, skip-if-present.
- **Per-case schema (the loader PR MUST verify against the live repo — this is the read-only-recon caveat, exactly the ambiguity M4.4b resolved on the 68000):** the 8088 vectors are well-known to be JSON arrays of cases, each with `name`, an `initial`/`final` (often `initial state`/`final state`) carrying `regs` (the 8086 register file: `ax bx cx dx cs ss ds es sp bp si di ip flags`) and `ram` (address/value byte pairs), a **`queue`** (the prefetched instruction-queue bytes — the 8088's prefetch queue, the analogue of the 68000's `prefetch` 2-word array, but **byte-granular and up to the 8088's 4-byte queue**), and a **`cycles`** array (the per-cycle bus trace: pin states / `ALE`/status/`RD`/`WR`/data — the 8088's bus-cycle protocol, *finer-grained and differently-shaped* than the 68000's `[dir, cycles, fc, addr, sizeTag, value]` transaction tuples).
- **Format unknowns the loader PR must confirm read-only against the live repo (flag, do not block):** (a) the exact JSON key names (`initial` vs `initial state`; `regs` sub-keys; whether `flags` is one value or split); (b) the exact **`cycles`** entry shape (the 8088 trace is a per-clock pin-state record, not a per-transaction tuple — the *correctness* axis needs only `regs`+`ram`+`queue` final state; the *cycles* trace is the timing axis, Decision 6); (c) whether files are **gzipped** (the 8088 set may ship plain `.json` per-opcode, unlike the 68000's `.json.gz` — confirm and parameterize the loader's decompression accordingly); (d) the file-keying (per-opcode-hex like the 6502, e.g. `00.json`, vs mnemonic-keyed like the 68000 — the 8088 set is **opcode-hex-keyed**, closer to the 6502 loader than the 68000 loader, so the loader may reuse `TomHarteVectors`' hex-keyed resolver shape rather than the 68000 mnemonic one — confirm).

**Decision: gate M5 on the `SingleStepTests/8088` set; the loader is a new `M8086TomHarteLoader` whose exact schema (key names, gzip-or-plain, hex-or-mnemonic keying, the `cycles` shape) the loader PR verifies read-only against the live repo first** (the M4.4b discipline — fetch a sample, confirm the schema, then build the loader). The **correctness gate** asserts `regs` + `ram` final state (+ `queue` once the prefetch axis lands); the **`cycles`/timing gate** is the late axis (Decision 6).

**Consequences.**
- *Good:* the loader-pattern + cache-dir + skip-attribute + fetch-script machinery all have proven templates (the 68000 set); the recon names the source repo and the likely schema so the loader PR starts from a known shape; separating the `regs`/`ram` correctness assertion from the `cycles` timing assertion is the lesson-learned baked in (Decision 6).
- *Bad / flagged:* the exact 8088 JSON schema (key names, gzip, keying, the `cycles` pin-state shape) is **not** fully determinable read-only from here with certainty — the loader PR must verify against the live repo as its first task (a known, bounded recon, not a blocker). The 8088 `cycles` trace is *finer-grained* than the 68000's (per-clock pin states), making the timing axis genuinely harder than the 68000's — another reason to sequence it late (Decision 6).

### Decision 6 (GUIDANCE — the M4.5a lesson-learned, baked in) — separate the DATA/correctness axis from the TIMING axis from the start; sequence timing into its own late sub-milestone

**The lesson.** M4.5a (the 68000 MOVE plan, the currently in-flight branch) hit a **gate-scoping bug**: the plan demanded the **cycle-accurate per-transaction trace + the cycle-count axis** as a *precondition* for the **register/RAM correctness axis**, even though the architecture (ADR 0003 §4 just-in-time item 3, ADR 0004 Decision 3) had already deferred timing/prefetch to a later sub-milestone. The vectors caught the over-specification (the MOVE bodies were correct on regs+RAM but the plan blocked green on the unbuilt timing trace). The fix is to **separate the axes in the plan from the start**.

**Decision (binding guidance for the M5 Planner):** the M5 milestone plan MUST separate two axes and sequence them:

1. **The DATA / correctness axis** (the early, primary axis): after executing each instruction, the **final register file + the final RAM state** match the vector's `final`. This is what M5.5a–c primarily gate on. It needs: the decode front-end, ModR/M+EA+segmentation, the op bodies, the flag computation — **but NOT** the per-cycle bus trace, NOT the cycle count, NOT the prefetch-queue final state.
2. **The TIMING axis** (the late, separate axis): the **per-cycle `cycles` bus trace, the cycle count, and the 8088 prefetch-instruction-queue (`queue`) final state**. This is genuinely harder for the 8088 than the 68000 (the 8088 trace is per-clock pin states, not per-transaction tuples — Decision 5), and the prefetch queue is a real mechanism (the 8088's 4-byte BIU queue) that must be modeled to assert `queue`. **Sequence this into its own late sub-milestone (M5.5d's tail or a dedicated M5.5e),** AFTER the correctness axis is green across the integer ISA.

**Concretely, the M5 plan must:** (a) make the early-family gates assert **`regs` + `ram` final state only** (a loader option/mode that diffs the data axis and ignores `cycles`/`queue`), exactly so a correct MOV/ALU body goes green without the timing machinery existing; (b) introduce the prefetch-queue model + the `cycles`-trace diff + the cycle-count check as a **late, explicit sub-milestone** with its own plan, not as a precondition baked into the MOV plan; (c) never make a later-axis artifact (the trace, the queue, the cycle count) a *blocking precondition* for an earlier-axis correctness PR. This is the direct generalization of the M4.5a fix to M5.

**Consequences.**
- *Good:* the M5 family PRs can reach correctness-green incrementally without the (hard, 8088-specific, per-clock) timing machinery existing first; the over-specification that bit M4.5a cannot recur; the timing axis gets the focused, late treatment it needs (the 8088 prefetch queue + per-clock trace is a real sub-project). This mirrors how M4 *should* have scoped MOVE.
- *Bad:* two gate modes (data-only vs full) add a little loader complexity (a known, small cost — a diff-mode flag). The timing axis being late means the 8088 is not cycle-accurate until the late sub-milestone — the accepted, explicit "correctness first, timing late" trade-off (the same one M4 accepted for the JIT speed).

## 3. The recommended M5 PR arc (the Planner expands PR-by-PR)

Dependency-ordered, each branch → PR. Mirrors ADR 0004 §3. The JIT hot-op emit is **not** in M5 (it is M6, built once for Z80+68000+8086 — ADR 0005 §5).

- **M5.0 — These ADRs (0005 + 0006).** No code. *(this document + its companion)*
- **M5.1 — State foundation.** The 8086 register file (pair-views `AX`/`AH`/`AL` etc., `SP`/`BP`/`SI`/`DI`, segment regs `CS/DS/ES/SS` as `General`, `IP`, `FLAGS`); the FLAGS `FlagLayout` + the new `Flag` members (`T`, direction; `H`-for-AF or `Af`); the 8086 partial skeleton + the `AddressSpace(addressBits:20, LittleEndian)` wiring. Prove 6502/Z80/68000 byte-identical. **Depends on:** M5.0. *(Mostly reuse — the lightest substrate PR of any architecture, because ADR 0005 found the state half is already general.)*
- **M5.2 — The decode front-end (the load-bearing PR).** The new `EmitX86DecodeWalk` arm + the x86 decode-structure variant (prefix-stacking, real ModR/M disp-length table, immediate-length rule, opcode-group keying); **ship the SHAPE + a synthetic variable-length-decode fixture** (the M3.1b/M4.3a discipline) before any 8086 dataset depends on it. The byte-granular EA descriptor carrier. **Depends on:** M5.1. *(Highest-risk M5 abstraction — the symmetric analogue of M4.3's field walk.)*
- **M5.3 — ModR/M EA + segmentation.** `EmitX86Ea` (the 16-bit EA table, the `mod=00,r/m=110` exception, the 16-bit-wrap) + the segment-resolution layer (`(seg<<4)+offset`, the default-segment-per-mode rule, the segment-override threading); the `reg`-as-register-vs-extension data. Synthetic + unit proof. **Depends on:** M5.2.
- **M5.4 — Importer x86 arm + the 8086 dataset/spec.** The third disjoint importer arm (x86 opcode-table + ModR/M/group/immediate/prefix metadata); extract + cross-source-diff a second x86 reference; emit a generator-clean `M8086Spec.cs` + `M8086RegeneratedSpecTests`; the new `M8086TomHarteLoader` (verify the live 8088 schema first — Decision 5). **Depends on:** M5.3.
- **M5.5 — The 8086 interpreter (correctness oracle) + the TomHarte gate.** The hand-written `M8086Cpu` partial + the op bodies, family-by-family, gated on the `SingleStepTests/8088` `regs`+`ram` final state (the DATA axis — Decision 6). **Splits:** **M5.5a** MOV + EA pipeline; **M5.5b** integer ALU + BCD + flags; **M5.5c** shift/rotate + stack + misc; **M5.5d** control flow + strings/`REP` + `IN`/`OUT` + interrupts. **Depends on:** M5.4.
- **M5.5e (or M5.5d's tail) — The TIMING axis (the late, separate sub-milestone — Decision 6).** The 8088 prefetch-instruction-queue model (to assert `queue`), the per-clock `cycles` bus-trace diff, the cycle-count check. Its own plan; AFTER the correctness axis is green. **Depends on:** M5.5a–d green.
- **M5.6 — The 8086 through the generic JIT as all-fallback (tier parity).** Wrap in `JittedCpu<M8086Cpu>`, drive the TomHarte-through-JIT sweep, prove byte-identical tier parity (the M3.5/M4.6 pattern; zero JIT-assembly change). **No hot-op emit** (M6). **Depends on:** M5.5.

**Sequence:**
```
M5.0 (ADRs 0005+0006)
  └─> M5.1 (state — light, mostly reuse)
        └─> M5.2 (x86 decode front-end — LOAD-BEARING, synthetic proof first)
              └─> M5.3 (ModR/M EA + segmentation)
                    └─> M5.4 (importer x86 arm + 8086 dataset/spec + 8088 loader)
                          └─> M5.5 (interpreter, DATA axis) [splits a–d, family-by-family]
                                ├─> M5.5e (TIMING axis: prefetch queue + cycles trace — LATE, separate)
                                └─> M5.6 (8086 through JIT, all-fallback)
   ──────────────────────────────────────────────> M6 (cross-arch JIT optimization: hot-op emit, built once for Z80+68000+8086)
```
**Likely to split:** M5.2 (the decode variant vs the synthetic fixture), M5.5 (a–d by family). **Estimated:** ~7 base chunks, realistically ~10 PRs with the splits — comparable to M4.

## 4. Decisions deliberately left "just-in-time"

1. **The exact x86 decode-structure variant record shape** (the prefix-role map + the per-opcode has-ModR/M / immediate-length / group metadata) — settle when M5.2/M5.4 have real 8086 opcode-table rows in hand from the extraction; the *commitment* (a new byte-granular variable-length arm, real ModR/M length, prefix stacking, opaque key reused) is firm, the record fields are not.
2. **Whether `REP`-string ops + the BCD `AAM`/`AAD` (which carry an immediate-base byte) need any operand-model extension** — depends on the operand model after M5.3; the `REP` loop is the Z80-block-op precedent (a one-instruction `CX`-counted loop), and the BCD immediate-base is a small operand — finalize at M5.5b/d.
3. **The exact 8088 TomHarte schema** (key names, gzip-or-plain, hex-or-mnemonic keying, the `cycles` pin-state shape) — the loader PR (M5.4) verifies read-only against the live `SingleStepTests/8088` repo as its first task (Decision 5); the *correctness-axis* assertion (`regs`+`ram`) is firm regardless.
4. **The prefetch-queue model fidelity** (how faithfully the 8088 BIU queue is modeled) — only the *late timing axis* (M5.5e) needs it; settle against the live `queue` field then.

## 5. Consequences summary + flags

- **Decode (load-bearing):** the FieldGrammar/word-decode model does **NOT** extend to the 8086; the existing byte walk gives only the *shape* of mid-stream length (a synthetic `modrm & 0x03` placeholder), not real x86 substance; so the 8086 gets a **third decode front-end** (`EmitX86DecodeWalk`) — but it reuses the opaque-key + computed-length + `DecodeResult` + descriptor-resolution **back-end** unchanged. Highest-risk M5 abstraction — prove with a synthetic fixture first.
- **ModR/M + EA:** a structured 8086 EA descriptor (`mod`/`reg`/`r/m`/disp/segOverride) → a new `EmitX86Ea` + the segment-resolution layer (`(seg<<4)+offset`); reuses the 68000 EA-descriptor *pattern* + the `EmitZ80IndexedEa` displacement seam; **no new `AddrMode` member**; *simpler* than the 68000 EA (no write-back side effect).
- **Importer:** a third disjoint arm (x86 opcode-table + metadata) + a third regen test; the 8088 TomHarte loader reuses the gzip/mnemonic-keyed *pattern* (schema verified live in M5.4).
- **Instruction set:** the real-mode 8086 integer ISA, family-by-family (MOV→ALU→shift/stack→control/strings/interrupts); `0F`/186+/protected-mode deferred; `IN`/`OUT` reuse the Z80 I/O-bus seam, `REP` the Z80 block-op precedent, `HLT` the generic `Halted`.
- **TomHarte:** gate on `SingleStepTests/8088`; loader-pattern/cache-dir/skip-attr/fetch-script have 68000 templates; the exact schema (key names, gzip, keying, `cycles` shape) is verified read-only by the loader PR first.
- **Lesson-learned (binding):** separate the DATA/correctness axis (`regs`+`ram` final state) from the TIMING axis (the per-clock `cycles` trace + cycle count + the prefetch `queue`); sequence timing into its own late sub-milestone (M5.5e); never make a timing artifact a blocking precondition for a correctness PR. This is the M4.5a gate-scoping fix, generalized to M5.
- **Reconciliation flags:**
  - The substrate's "8086 ModR/M" hooks (`DecodeStructure.ModRmOpcodes`/`SubFieldOpcodes`, `LengthRule.ModRmDetermined`) are **proof-of-shape placeholders only** (no live CPU declares them; `modrm & 0x03` is synthetic). The real 8086 decode is a new arm, not a finishing of the placeholder — do not under-scope it as "the synthetic path, done."
  - The 8088 `cycles` trace is **finer-grained** than the 68000's `[dir,cycles,fc,addr,sizeTag,value]` transaction tuples (per-clock pin states), making the timing axis genuinely harder — a primary reason it is sequenced late.
  - The exact `SingleStepTests/8088` JSON schema is **not fully determinable read-only from this pass**; the loader PR (M5.4) must verify it against the live repo first (the known, bounded M4.4b-style recon — a flagged first task, not a blocker).
