# Plan — V80-3: THE HEADLINE — CP/M 3.1 `A>` in 80 columns on the Videx (`ActiveIndex==1` from a real boot)

> **Arc:** apl2cpm3 CP/M 3.1 on the SoftCard + Videx — the 80-column CP/M sub-arc (ADR 0018). **PR 3 of 3 — the deliverable.**
> **Depends on:** V80-2 (CP/M 3.1 must reach `A>` in 40-col first; the boot must reach the BIOS for `icrt` to drive the Videx).
> **Grounded against:** `main` @ `7dacd6d` + the merged V80-1 (the slot param) + V80-2 (the 40-col `A>` boot). Re-ground all literal code against the *then-current* main when this PR is taken.
> **ADR:** ADR 0018 Decision 4 (the 80-col gate — the headline) + §1.3 (the Videx path is wired + waiting) + §1.4 (apl2cpm3 is the first real CP/M to engage the Videx). **Closes ADR 0017 OQ2 / Decision 6's open sibling-gate** (`ActiveIndex==1` from a real CP/M boot).
> **Queue row:** **V80-3** (THE 80-col headline).

## Why this PR

This is the genuine **80-column CP/M console end-to-end** — what the CPM-5 / ADR 0017 PR-5 re-frame stood in
for. The 2.2 master (and all five 2.2 candidates) are 40-column consoles (zero `$C0Bx`), so none engaged the
Videx (`ActiveIndex` stayed 0 — CPM-5's honest re-frame). **apl2cpm3 is different:** its README *requires* an
80-column card in slot 3, and its BIOS `icrt` routine drives the Videx CRTC via slot-3 `$C0B0/$C0B1` (ADR 0018
§1.1, §1.3). So apl2cpm3 is the **first realistic candidate to make `DisplayMultiplexer.ActiveIndex==1` true
from a real CP/M boot** — the headline of this sub-arc (ADR 0018 §1.4).

With V80-2 the boot reaches `A>` (the BIOS runs). This PR composes the apl2cpm3 SoftCard board at slot 4 **with
the Videx** (slot 3), runs the real boot, and asserts the decoded CP/M-3 console on the **Videx 80×24 render**
+ `DisplayMultiplexer.ActiveIndex==1` (the auto-switch fired). Everything needed is **already wired** (ADR 0018
§1.3): the IOU delegates `$C0B0-$C0BF` to the `VidexVideoterm`, the `$C800` firmware window + `$CC00` VRAM are
on `SoftCardVidexBoard`, and the `DisplayMultiplexer` auto-switch (`videx.ActiveChanged → SetActive`) is live.
The Videx path is wired and waiting; this PR is gated only on the boot reaching the BIOS (V80-2) + closing any
residual Videx-init bring-up against the live disk.

**Definition of done:** the live apl2cpm3 Disk 1 renders **CP/M 3.1 `A>` in 80 columns on the Videx** with
`ActiveIndex==1` from a real boot: the decoded console text on the Videx 80×24 render + `videxEngagedCount>0`
+ `mux.ActiveIndex==1` + `CoprocessorActive`. The Videx frame hash is captured. ROADMAP + ADR 0016 §O wording
updated: the "80-col CP/M end-to-end" headline is **achieved** by apl2cpm3. **This is the deliverable.**

## TDD discipline for the headline gate

The un-fakeable oracle is the **live disk** rendering CP/M-3 `A>` on the Videx 80×24 with `ActiveIndex==1`
(ADR 0018 Decision 4). The loop:

1. **Red:** write the 80-col gate (Task 1) asserting `ActiveIndex==1` + the decoded Videx console. With the
   asset staged, run it → it either PASSES immediately (if `icrt` drives the Videx with no further bring-up —
   the wired-and-waiting hope) or FAILS at `ActiveIndex==1` (the Videx-init residual — Task 2 triage).
2. **Triage (Task 2, only if red):** instrument the boot to confirm `icrt` reaches `$C0B0/$C0B1` and the
   `ActiveChanged` wiring fires; close any bounded Videx-init item against the live disk (no new abstraction —
   the `$C0Bx`/`$CC00` seams are shipped).
3. **Green:** the gate passes; capture the Videx 80×24 frame hash (Task 3).
4. **Sibling gate (Task 4):** assert `ActiveIndex==1` for apl2cpm3 vs the 2.2 master's `ActiveIndex==0` (the
   contrast that proves the auto-switch is real, not faked).

No task is "done" until the live 80-col gate is green AND the full `SoftCard*`/`Videx*`/`Apl2Cpm3*` lanes are
green AND the 2.2 CPM-4/CPM-5 gates pass unchanged.

## Task 1 — The 80-col Videx CP/M-3 gate (`ActiveIndex==1` from a real boot)

### 1a. The gate

Add to `tests/CpuEmulator.Tests/Apple2/Apl2Cpm3BootTests.cs` (or a sibling `Apl2Cpm3VidexBootTests.cs`). The
build path mirrors the shipped `SoftCardVidexBoardTests.Cpm_boots_and_renders_the_A_prompt_on_the_Videx_80col_interpreter`
(lines 148-197) exactly — the same `DisplayMultiplexer([video, videx])` + `videx.ActiveChanged` wiring the
production `SoftCardVidexSurface` uses — but over the apl2cpm3 board at **slot 4**, and the assertions flip
from CPM-5's `ActiveIndex==0` (the 40-col hardware truth for the 2.2 master) to **`ActiveIndex==1`** (the real
80-col engagement, the headline):

```csharp
    // ADR 0018 PR-3 (V80-3) -- THE HEADLINE DELIVERABLE: CP/M 3.1 A> in 80 columns on the Videx, ActiveIndex==1
    // from a real boot. apl2cpm3's BIOS icrt drives the Videx slot-3 CRTC ($C0B0/$C0B1), so the production
    // auto-switch (videx.ActiveChanged -> mux.SetActive) fires and the multiplexer follows to the Videx 80-col
    // source. This is the FIRST time ActiveIndex==1 is asserted against a real CP/M boot (closes ADR 0017 OQ2 /
    // Decision 6's open sibling-gate). Un-fakeable: the disk must actually program the CRTC (zero $C0Bx -> no
    // switch -> ActiveIndex stays 0 -> RED), and A> must decode off the Videx 80x24 VRAM render.
    [Apl2Cpm3Fact]
    public void Cpm3_boots_to_the_A_prompt_in_80col_on_the_Videx_interpreter()
    {
        var (systemRomPath, disk1Path) = Apl2Cpm3Vectors.TryGetAssets()!.Value;
        byte[] systemRom = Apple2Rom.Load(systemRomPath);
        byte[] diskBootRom = Apple2Rom.TryLoadDiskRom()
            ?? throw new InvalidOperationException("the slot-6 disk2.rom is required for the apl2cpm3 boot gate");
        byte[]? videxCharRom = VidexRom.TryLoadCharRom();   // null -> the synthetic VidexFont (structural render)
        IBlockDevice disk1 = Apl2Cpm3.LoadBootDisk(disk1Path);

        // Build the SoftCard+Videx board at SLOT 4 (apl2cpm3's slot), tracking the Videx auto-switch the
        // production SoftCardVidexSurface wires: ActiveChanged -> the multiplexer follows.
        var state = new Apple2VideoState();
        var lc = new Apple2LanguageCard(systemRom);
        var drive1 = new DskFluxImage(disk1, SectorOrderKind.Cpm);
        var disk = new Apple2DiskII(drive1);
        var videx = new VidexVideoterm(videxCharRom);   // see grounding note on the ctor below
        var iou = new Apple2Iou(state, lc, disk, videx);
        BoardSpec spec = SoftCardVidexBoard.Spec(systemRom, iou, disk, diskBootRom, videx,
            controlPortBase: SoftCardBoard.ControlPortBaseSlot4);   // THE SLOT FIX (V80-1)
        Machine machine = BoardMachineFactory.Build(spec);          // interpreter tier (the coprocessor is interpreter)
        var video = new Apple2Video(machine.Space(AddressSpaceKind.Program), state);

        var mux = new DisplayMultiplexer([video, videx], initialActive: 0);
        int videxEngagedCount = 0;
        videx.ActiveChanged += active =>
        {
            if (active) videxEngagedCount++;
            mux.SetActive(active ? 1 : 0);
        };

        machine.Reset();
        machine.Run(CpmBootCycles);                          // the real $C600 -> tracks -> $C400 -> CP/M-3 -> icrt

        // --- (1) THE HEADLINE: the Videx 80-col engaged from a real CP/M boot (icrt drove the CRTC).
        Assert.True(videxEngagedCount > 0,
            "expected apl2cpm3's icrt to engage the Videx (videx.ActiveChanged should have fired)");
        Assert.Equal(1, mux.ActiveIndex);                    // the multiplexer auto-switched to the Videx 80-col

        // --- (2) The Z80 ran (the $C400 handoff fired).
        Assert.True(machine.CoprocessorActive,
            "expected the Z80 to be the active bus master after the apl2cpm3 boot handoff");

        // --- (3) The decoded CP/M-3 console on the VIDEX 80x24 render (not the Apple 40-col page): A> + a
        //         CP/M-3 sign-on substring decoded from the $CC00 VRAM through the char ROM. The Videx is the
        //         active source (ActiveIndex==1), so its render IS the console.
        string videxConsole = DecodeVidexConsole(videx);
        Assert.Contains("A>", videxConsole);   // the CCP prompt on the 80-col terminal -- the deliverable
        Assert.True(
            videxConsole.Contains("CP/M V3", StringComparison.OrdinalIgnoreCase)
            || videxConsole.Contains("DIGITAL RESEARCH", StringComparison.OrdinalIgnoreCase)
            || videxConsole.Contains("CP/M", StringComparison.OrdinalIgnoreCase),
            $"expected a CP/M-3 sign-on line on the Videx console; decoded was:\n{videxConsole}");
    }

    /// <summary>Decode the Videx 80x24 character VRAM ($CC00 window, via VidexVideoterm) to ASCII -- the
    /// terminal console text. Reads the live VRAM cells the CRTC addresses and maps each character code to
    /// ASCII (the Videx stores 7-bit ASCII char codes). Returns the 24 rows joined.</summary>
    private static string DecodeVidexConsole(VidexVideoterm videx)
    {
        var rows = new string[24];
        for (int r = 0; r < 24; r++)
        {
            var sb = new System.Text.StringBuilder(80);
            for (int c = 0; c < 80; c++)
            {
                int code = videx.PeekVramForTest(r, c) & 0x7F;   // see grounding note -- the shipped peek seam
                sb.Append(code is >= 0x20 and <= 0x7E ? (char)code : ' ');
            }
            rows[r] = sb.ToString();
        }
        return string.Join("\n", rows);
    }
```

> **Grounding notes (verify against the then-current main; some are V80-3-time confirmations):**
> - `VidexVideoterm.ActiveChanged` is `event Action<bool>?` (confirmed: `SoftCardVidexSurface` wires
>   `videx.ActiveChanged += active => mux.SetActive(...)`; the shipped CPM-5 gate uses the same shape).
> - `DisplayMultiplexer([sources], initialActive: 0)` + `SetActive(int)` + `ActiveIndex` are the shipped
>   members (confirmed in `DisplayMultiplexer.cs`; used live in the CPM-5 gate, `SoftCardVidexBoardTests.cs:169`).
> - **`PeekVramForTest(row, col)`** is the shipped Videx VRAM peek seam — the CPM-5 board-wiring test uses
>   `videx.PeekVramForTest(0, 0)` (`SoftCardVidexBoardTests.cs:43`). **Confirm its (row, col) vs (offset)
>   signature at V80-3 time;** if it takes a flat VRAM offset rather than (row, col), the decoder maps
>   `row*80 + col` (the 80-col layout) or reads the CRTC start-address register. If no row/col peek exists,
>   the fallback is `VidexVideoterm`'s render-to-RGBA path + the synthetic `VidexFont` (the PR-N direct-render
>   gates decode structural ink) — but the ASCII-from-VRAM peek is the cleaner console oracle. The Builder
>   picks whichever the shipped Videx API exposes; the substring assertion is identical.
> - **`new VidexVideoterm(videxCharRom)`**: confirm the ctor — the shipped tests use the **parameterless**
>   `new VidexVideoterm()` (the synthetic font; `SoftCardVidexBoardTests.cs:23,59,163`). If the char ROM is
>   optional/internal, use `new VidexVideoterm()` and let `VidexRom.TryLoadCharRom()` feed the *render* path
>   only where needed. The console-text decode (codes, not glyphs) does NOT need the char ROM, so
>   parameterless is fine for the substring assertion; the char ROM only sharpens the *PNG* (Task 3).
> - `CpmBootCycles` is the V80-2 const (20 M) — share it or re-declare; tune on first green.

## Task 2 — Close any Videx-init residual against the live disk (triage, only if Task 1 is red)

ADR 0018 PR-3: "Close any Videx-init bring-up against the live disk (the CRTC programming + VRAM writes flow
through the already-wired `$C0Bx`/`$CC00` seams — no new abstraction)." If Task 1 fails at `ActiveIndex==1`:

1. **Confirm `icrt` reaches the CRTC.** Instrument (throwaway probe, reverted) the `$C0B0/$C0B1` accesses
   during the boot — does the Z80-side BIOS `icrt` actually write the CRTC init table (R1=`$50`/R6=`$18`, the
   80×24 geometry — the PR-N init pattern)? The README confirms `icrt` inits the 80-col card; the live boot
   confirms whether our slot-3 `$C0Bx` IOU delegate sees it.
2. **Confirm the `ActiveChanged` trigger.** `VidexVideoterm` raises `ActiveChanged(true)` when it is enabled
   (the PR-N seam). Verify the enable condition the disk drives (the `$C0Bx` soft-switch or the CRTC program)
   maps to the `ActiveChanged` fire. If the disk uses a Videx-enable mechanism our `VidexVideoterm` does not
   yet recognize, that is the bounded bring-up item — close it on the shipped seam (no new abstraction).
3. **Confirm VRAM writes land.** The CP/M-3 CONOUT writes characters to the `$CC00` VRAM (banked). Confirm the
   console text appears in `PeekVramForTest` — if the Videx firmware window banking (`$C800`) isn't engaged so
   the BIOS's VRAM writes miss, that is the residual (the `$C800` mapper is the shipped 2nd `Remap` consumer,
   PR-N — verify it banks correctly for apl2cpm3's access pattern).

> **Scope guard:** this is bring-up against shipped seams (`$C0Bx` IOU delegate, the `$C800` Remap mapper, the
> `$CC00` VRAM, the `ActiveChanged` event) — NOT a new abstraction. If the triage reveals a genuinely missing
> Videx capability (judged unlikely — the README's hardware matches our wiring), record it and assess whether
> it is a bounded addition or an owner escalation. Most likely outcome: the path is wired-and-waiting and Task
> 1 passes with no production change (the ADR §1.3 prediction).

## Drift / risk from ADR 0018 (flag in the PR body)

1. **The Videx-init bring-up (Task 2) is determined live, not pre-designed** (ADR 0018 PR-3). The plan
   specifies the triage steps + the shipped seams each touches; the most likely outcome is "wired-and-waiting,
   no production change" (ADR §1.3). If a bounded Videx-init item surfaces, it is closed on the shipped seam.
2. **The Videx console decode uses `PeekVramForTest`** (the shipped Videx VRAM peek). Its exact signature
   ((row,col) vs flat offset) is confirmed at V80-3 time — the grounding note gives the fallbacks (the
   render-to-RGBA + `VidexFont` direct-decode path the PR-N gates already use). The substring assertion is
   identical regardless of which decode the shipped API exposes.
3. **40-col vs 80-col staging (ADR 0018 OQ2):** if V80-2 found that apl2cpm3 goes *straight* to 80-col (never
   painting the 40-col page), the V80-2 40-col gate was re-scoped (per V80-2's drift note) and this PR is the
   sole `A>` gate — note the dependency outcome here. If apl2cpm3 paints 40-col *then* switches to 80-col, both
   gates assert their respective consoles (40-col early sign-on; 80-col settled `A>`).
4. **Clock ratio / cycle budget (OQ4):** CP/M-3's loader chain + the `icrt` Videx init may need more cycles to
   settle the 80-col console than the 40-col `A>` — tune `CpmBootCycles` on the first green run (confirm the
   Videx console is settled, byte-stable, before the budget). No new timing risk expected (coarse-timed
   workload at ratio 2.0).
5. **This closes the sub-arc.** With V80-3 merged, apl2cpm3 CP/M 3.1 boots to `A>` in 80 columns on the Videx —
   the true 80-col CP/M end-to-end the 2.2 arc could not produce. Optional follow-on (NOT in this batch): a
   multi-drive UAT with Disks 2-7 (`EMULA.COM`, dev tools) — fetch those disks only if scheduled (ADR 0018
   Decision 5 / §3).
