## Why this PR

With V80-1 merged, the slot fix is live and ADR 0018-A's skew fix is proven: building the SoftCard board at slot
4 over apl2cpm3 Disk 1 (boot track 0 in raw DOS 3.3 order) makes the Z80 activate, `$31` (`LD SP`) lands at Z80
`$0100`, CPMLDR loads contiguously and **runs forward** — `$0100` entry → BIOS init → BDOS `open` of `"CPM3 SYS"`.
But the boot does **not** reach `A>` because the **`?jsr65` Z80→6502 service-loop bridge is dead** — ADR 0018-B §3
proves the cause: CP/M-3's LDRBIOS does every I/O (the `CPM3.SYS` floppy read via `?fdrwts`, the console via
`?odcrt`) by toggling the bus to the 6502 and waiting for the 6502's `L65A` service loop ($03C0) to run the sub
and `STA $C400` the bus back. **Our handoff has no PC redirection, so the 6502 resumes at BOOTLDR's stale
`STA $C400 / RTS` overlay ($03C9) instead of `L65A`** — `?fdrwts` never runs (the `CPM3.SYS` read returns
`A=$FF`, the Z80 `DI/HALT`s at `$01A9`) AND `?odcrt` never runs (zero console output). One dead bridge, both
symptoms (live trace: a single `6502→Z80` transition, zero hand-backs).

This PR lands the **combined fix**: **(2a)** ADR 0018-A's track-0 DOS33 skew correction **+** **(2b)** the
ADR 0018-B `?jsr65` bridge fix (a per-board "6502 resume entry on bus-hand-to-6502", defaulted off so 2.2 is
byte-for-byte unchanged). The arbiter is decoded `A>` on screen; the fast discriminators are `$31` at Z80
`$0100` (the skew, Task 3a-bis) and **≥1 `Z80→6502` bus hand-back** (the bridge, Task 3a-ter).

**This is a bounded, PINNED fix** (not open-ended triage): ADR 0018-A + 0018-B give both mechanisms, the live
signatures, and the targets. The skew change is an additive, apl2cpm3-scoped `DskFluxImage` ordering; the bridge
change is an additive optional parameter on the existing per-board `ICoprocessorControl` / `SoftCardBoard.Spec`
handoff seam (the seam ADR 0017 D3 already amended) — **the shared 2.2 path and the Z80 core are untouched** (the
2.2 board passes no resume entry → `null` → today's resume-at-suspended-PC, byte-for-byte).

**Definition of done:** the live apl2cpm3 Disk 1 boots to **CP/M 3.1 `A>`** on the 40-col Apple console
(`$0400` text page): the decoded-text gate asserts the `A>` CCP prompt + a CP/M-3 sign-on substring

### What the ADR already established (do NOT re-derive)

- The slot-4 handshake fires: the Z80 activates on the single `$C400` write (~2.4 M cycles); the CPMLDR

- The Z80 resets to `PC=$0000` (= 6502 `$1000`), which is **all zeros**, so it NOP-slides

### The ordered hypotheses (ADR 0018 Decision 3 — confirm/falsify live, in this order)

Build a throwaway `BootProbe` mode (or a temporary xunit `[Fact(Skip-removed)]`) over the slot-4 apl2cpm3
board, instruction-step the boot, and answer each in order:

**H1 (the likely crux) — the entry vector at the Z80 reset address.** Step the 6502's start-Z80 routine

staged disk) and the boot2/CPMLDR stages. Determine:
- Does any 6502 (or Z80) stage write a `JP <loader>` stub at physical `$1000` (the Z80's `$0000`) **before**
  the Z80 is released? Dump physical `$1000-$1010` at the moment of the `$C400` write. If it is all zeros at
  release, the loader expects the Z80 to start *somewhere else* (not `$0000`) OR a later stage should write
  the stub.

  at `$1100+` has a known entry — dump `$1100-$1120` and disassemble as Z80)? CP/M-3 `CPMLDR` conventionally

**H2 — a later boot2/CPMLDR stage writes the stub after the first toggle (a multi-round-trip handshake).** If
H1 shows the stub *would* be written by a 6502 stage that only runs after the Z80 hands control back, then

NOP-slide and confirm it never reaches an `$E400` write (consistent with the single-toggle observation →

## Task 2a — Land the apl2cpm3 boot-read sector-skew correction (PINNED by ADR 0018-A; SOLVED live)

> **This is the SOLVED first half of the combined fix.** The Builder already live-verified the table: present
> apl2cpm3's boot **track 0 ONLY** in raw DOS 3.3 order (`Apple2SectorOrder.Dos33PhysToLog` =
> `[0,7,14,6,13,5,12,4,11,3,10,2,9,1,8,15]`); **tracks 1–2 KEEP `CpmBootPhysToLog`** (applying DOS33 to tracks
> 1–2 crashes 6502 BOOTLDR with an undefined opcode — CPMLDR's entry/BIOS/sign-on are all on track 0, the
> track-1 tail is `$E5` padding); `table[0]==0` is mandatory (physical sector 0 must hold the boot sector). This
> is ADR 0018-A Decision A2-ii. **Land it as a new `SectorOrderKind.Cpm3`** whose `(kind, track)` overload returns
> `Dos33PhysToLog` for track 0 and the existing CP/M boot/data tables for tracks 1+; the apl2cpm3 board constructs
> `new DskFluxImage(disk1, SectorOrderKind.Cpm3)`, the 2.2 board keeps `SectorOrderKind.Cpm` **byte-for-byte
> unchanged**. (Equivalent: A2-i, a single composed table — but A2-ii's track-0-raw is the live-pinned, minimal
> form. Use whichever the Builder's reverted probe proved; the §3.1 math + the `$31`-at-`$0100` check are the
> arbiter.) The reference material below is retained for the composition derivation.

**The root cause is proven (ADR 0018-A §3): a double sector-skew.** apl2cpm3's `BOOTLDR.MAC` reads `CPMLDR.COM`
through the Disk II interface ROM (`JMP (a2l)` → `$Cn5C`) with its **own** software skew
`xlt = [13,10,7,4,1,14,11,8,5,2,15,12,9,6,3,0]`; our `DskFluxImage` **already pre-applies**
`CpmBootPhysToLog = [0,11,6,1,12,7,2,13,8,3,14,9,4,15,10,5]` to system tracks 0–2 (ADR 0017 Decision 1). The two
compose, so CPMLDR's 18 pages load **contiguously into the right window (`$1100–$20FF`) but page-permuted** — and
the byte that should be `$31` (`LD SP`, CPMLDR's entry) at Z80 `$0100` is instead `$E9` (`JP (HL)`, file page 14),
so the Z80's NOP slide loops at `$0100` forever. The composition reproduces the measured permutation 15/15 on
track 0 (0018-A §3.1). **CPMLDR lives on `.dsk` tracks 0–1 (system tracks).**

**The fix is an additive, apl2cpm3-scoped `DskFluxImage` skew correction** (ADR 0018-A Decision A2) — choose, by
building it and checking the load against the live disk:

### Outcome A2-i (recommended) — a new `SectorOrderKind.Cpm3` (or an apl2cpm3 flag) whose table cancels BOOTLDR's `xlt`

Add an enum value `SectorOrderKind.Cpm3` to `Apple2SectorOrder` with a physical→logical table (and the per-track
boot/data split) such that the **net** skew an `xlt`-translating reader sees is identity-correct on apl2cpm3's
boot tracks. The apl2cpm3 board/gate constructs `new DskFluxImage(disk1, SectorOrderKind.Cpm3)`; the 2.2 board
keeps `SectorOrderKind.Cpm` **byte-for-byte unchanged** (the load-bearing invariant — CPM-4 hash + CPM-5 Videx
gates must stay green). Derive the table from the composition in 0018-A §3.1 (the `xlt`-cancelling map), then
**verify against the live disk** — the load-correctness check (Task 3a-bis) and the `A>` gate are the un-fakeable
proof. This is the cleanest seam: additive enum + one table + the apl2cpm3 wiring point.

### Outcome A2-ii — present the apl2cpm3 boot tracks in raw/identity DOS order (no pre-skew)

If the only `xlt`-translated reads are the boot/CPMLDR load (tracks 0–1) and the running CP/M BIOS RWTS reads the
data tracks with a *different* (un-`xlt`'d) convention, present apl2cpm3's **boot** tracks raw (identity) so
BOOTLDR's own `xlt` is the sole skew, while the data tracks keep the existing `Cpm` data skew. The live boot
confirms which reader touches which tracks (0018-A OQ1). Same per-board `DskFluxImage(disk, kind)` seam.

> **What does NOT happen (voided branches):** the original Outcome (1) "no production change" is void — the slot

## Task 2b — Land the `?jsr65` Z80→6502 service-loop bridge fix (the gating third layer — PINNED by ADR 0018-B)

**The root cause is proven (ADR 0018-B §2-3): CP/M-3's LDRBIOS calls back into the 6502 via `?jsr65`, and our
bus handoff never resumes the 6502 at its service loop.** The LDRBIOS pattern (recovered from apl2cpm3's own
`LDRBIOS.MAC` + `DEVICE65.MAC`, the latter extracted from the Disk 6/7 images):

```
?jsr65: LD (a$vec),DE    ; a$vec = $F3D0 (Z80) -> Apple $03D0 (branch 6): the 6502 sub to call (?fdrwts / ?odcrt)
        LD (z$cpu),A      ; z$cpu = the Z80-side slot-4 toggle: HAND THE BUS TO THE 6502
        RET               ; ...the Z80 continues only AFTER the 6502 ran the sub and toggled the bus BACK
```
The 6502 side is the **`L65A` service loop** at Apple **`$03C0`** (`DEVICE65.MAC`, `.phase $3C0`): it runs the sub
at `a$vec`, then `STA a$cpu` (= `STA $C400`) to hand the bus back to the Z80, then `JMP L65A` to wait for the next
call. **Our `Machine.SetCoprocessorActive` (`src/CpuEmulator.Core/Machine.cs:97-101`) flips a boolean with no PC
redirect, so the 6502 resumes at BOOTLDR's stale `STA $C400 / RTS` overlay (`servt`=`$03C6`, the suspended PC is
the `RTS` at `$03C9`) — it returns up BOOTLDR's stack and NEVER enters `L65A`, so neither `?fdrwts` nor `?odcrt`
runs.** Live signature: exactly ONE `6502→Z80` transition (6502 suspended at `$03C9`), zero hand-backs.

**The fix is an additive, apl2cpm3-scoped, 2.2-defaulted-safe "6502 resume entry on bus-hand-to-6502"** on the
existing handoff seam (ADR 0018-B Decision B2). The shape (B2-i, recommended):

1. **Extend the handoff contract.** Add an optional 6502 resume entry to `ICoprocessorControl` /
   `SoftCardControlPort` so that the toggle which activates the **6502** (the Z80's `$EN00`/`$C400` write) sets
   the **primary (6502) PC** to a configured service-loop entry before the 6502 runs; the toggle that activates
   the **Z80** leaves the Z80 PC alone (it resumes after `?jsr65`). Two viable plumbings — pick the one that fits
   the existing seam cleanest:
   - a sibling method `void SetPrimaryResumeEntry(uint? pc)` on `ICoprocessorControl` that the control port calls
     (carrying a per-board entry), **or**
   - an overload `SetCoprocessorActive(bool active, uint? primaryResumePc)`.
   `RunDualCpu` consumes it when resuming the primary after a `6502←Z80` toggle (around
   `src/CpuEmulator.Core/Machine.cs:166`): if a resume entry is configured, set `Cpu.SetRegister("PC", entry)`
   (the shipped register-access pattern) before the next 6502 `Step()`.
2. **Carry the entry per-board.** Add an optional `coprocessorResumeEntry` (or `primaryResumeEntry`) parameter to
   `SoftCardBoard.Spec` / `SoftCardVidexBoard.Spec` — **a sibling of V80-1's `controlPortBase`, defaulted to
   `null` so the 2.2 board is byte-for-byte unchanged** (null → today's resume-at-suspended-PC, which 2.2 relies
   on). The apl2cpm3 board passes the LDRBIOS service entry. The control port reads it from its Realize context
   (the same way it reads `ICoprocessorControl`).
3. **Pin the exact entry + trigger LIVE (the bring-up — bounded, candidates pinned).** The candidates are
   `$03C0` (`L65A`), `$03C6` (`servt`), `$03D0` (`a$vec`'s dispatch). The discriminator is the §3a-ter bus
   round-trip check (≥1 `Z80→6502` hand-back) + the 6502 PC reaching `L65A`. If a direct PC-set proves
   insufficient (the real card may assert the 6502 NMI/IRQ/RESET vector on hand-back — LDRBIOS points
   RESET/NMI/BRK at `L65A`), fall to B2-ii (model the vector fetch on the `6502←Z80` toggle). Build it, step the
   live boot, confirm the round-trip, record the chosen entry + evidence in the PR body (the ADR-0017-Decision-4
   discipline). **Revert any throwaway probe before the PR.**

> **What does NOT change (the invariant — and why 2.2 is safe):** CP/M **2.2** loads via 6502 boot2 BEFORE the
> Z80 BIOS is live and paints its screen through the TRANSLATED BUS (branch 6) — it **never calls the 6502 back**
> via a `?jsr65`-style synchronous bridge (ADR 0018-B §3.2; ADR 0017 §1). So the 2.2 board passes no resume entry
> (`null`), gets today's resume-at-suspended-PC, and the CPM-4 committed-hash `A>` gate + the CPM-3 `$Axxx`-stable
> gate pass byte-for-byte. **Do NOT change the Z80 core, `SoftCardTranslation`, `CoprocessorSpec`, or the 2.2
> board's construction.** The only touched files: `ICoprocessorControl.cs`, `Machine.cs` (`SetCoprocessorActive`
> + `RunDualCpu`'s primary-resume), `SoftCardControlPort.cs`, `SoftCardBoard.cs` / `SoftCardVidexBoard.cs` (the
> optional defaulted `Spec` parameter), and the apl2cpm3 wiring point.

> **Regression gate (un-fakeable):** (a) an asset-free unit test that a board built WITH a resume entry sets the
> primary PC on the `6502←Z80` toggle and a board built WITHOUT one (the 2.2 default) does NOT — the `false` row
> would only pass under a both-behaviors fiction (the V80-1 slot-placement-test discipline); (b) the live bus
> round-trip check (Task 3a-ter): ≥1 `Z80→6502` hand-back during the boot (today: 0). The 2.2 handoff (no resume
> entry) is byte-for-byte unchanged.

```csharp
        var disk = new Apple2DiskII(drive1);
        var iou = new Apple2Iou(state, lc, disk);
        // THE SLOT FIX (V80-1): apl2cpm3 hard-codes STA $C400 -> the control port decodes at slot 4.
        BoardSpec spec = SoftCardBoard.Spec(systemRom, iou, disk, diskBootRom,
            controlPortBase: SoftCardBoard.ControlPortBaseSlot4);
        Machine machine = BoardMachineFactory.Build(spec);   // interpreter tier (the coprocessor is interpreter)

        machine.Reset();
        machine.Run(CpmBootCycles);                          // the real $C600 -> tracks -> $C400 -> CP/M-3 boot

        // --- (1) The un-fakeable content oracle: decode the 40-col text page and assert the CP/M-3 prompt.
        string[] screen = DecodeTextScreen(machine);
        string joined = string.Join("\n", screen);
        Assert.Contains("A>", joined);   // the CCP prompt -- the headline target

        // --- (2) A CP/M-3 sign-on substring (the disk's own ASCII pins these -- live-verified on the staged
        //         disk: "CP/M V3.0 Loader" / "Copyright (C) 1982, Digital Research" / "CP/M Version 3.0").
        //         The exact line that survives to the settled console is confirmed on the first green run
        //         (ADR 0018 OQ2: the BIOS may paint 40-col then switch, or go straight to 80-col -- the gate
        //         asserts whichever the disk actually paints to the 40-col page).
        Assert.True(
            joined.Contains("CP/M V3", StringComparison.OrdinalIgnoreCase)
            || joined.Contains("DIGITAL RESEARCH", StringComparison.OrdinalIgnoreCase)
            || joined.Contains("CP/M", StringComparison.OrdinalIgnoreCase),
            $"expected a CP/M-3 sign-on line on the console; decoded screen was:\n{joined}");

        // --- (3) The Z80 ran: it became the bus master during the boot (the $C400 handoff fired).
        Assert.True(machine.CoprocessorActive,
            "expected the Z80 to be the active bus master after the apl2cpm3 boot handoff");
    }

    /// <summary>Decode the live 24x40 Apple text page ($0400, page 1) to ASCII -- the same TextRowBase walk
    /// the 2.2 SoftCard gate uses, stripping the normal-video high bit; non-printable cells become spaces.</summary>
    private static string[] DecodeTextScreen(Machine machine)
    {
        IAddressSpace bus = machine.Space(AddressSpaceKind.Program);
        var rows = new string[24];
        for (int r = 0; r < 24; r++)
        {
            uint rowBase = Apple2HiResAddress.TextRowBase(r, page2: false);
            var sb = new System.Text.StringBuilder(40);
            for (int c = 0; c < 40; c++)
            {
                int g = bus.Read8(rowBase + (uint)c) & 0x7F;   // strip the normal-video high bit
                sb.Append(g is >= 0x20 and <= 0x7E ? (char)g : ' ');
            }
            rows[r] = sb.ToString();
        }
        return rows;
    }
}
```

> **Why this is honest, not a cover:** `A>` at the `$0400` text page can only appear after a real CP/M-3
> CONOUT, which requires the Z80 to have entered the loaded BIOS through the slot-4 handshake (the CP/M-3 RAM
> maps to physical `$1000+` via translation branch 1, never the `$0400` text page — the exact argument the
> CPM-4 reviewer confirmed for the 2.2 gate). The Z80 NOP-sliding from `$0000` (the pre-bring-up state) never
> paints `A>`, so the gate FAILS until the entry handoff is closed and PASSES only on a real boot.

## Drift / risk from ADR 0018 (flag in the PR body)

1. **The bring-up is PINNED by ADR 0018-A + 0018-B (not open-ended triage), and is TWO layered fixes in one PR.**
   Layer 2a (skew): the mechanism (double sector-skew), the math (0018-A §3.1), and the target (`$31` at Z80
   `$0100`) are proven and SOLVED live (track-0 DOS33, `SectorOrderKind.Cpm3`). Layer 2b (bridge): the mechanism
   (the dead `?jsr65` Z80→6502 service-loop bridge — the 6502 resumes at `$03C9` not `L65A`/`$03C0`), the live
   signature (a single `6502→Z80` transition, zero hand-backs), and the fix shape (a per-board 6502 resume entry
   on the handoff seam, 2.2-defaulted-off) are proven in 0018-B §2-4. **Neither fix alone reaches `A>`** — the
   skew gets CPMLDR running; the bridge gets `?fdrwts`/`?odcrt` running. Land both; the live `A>` is the arbiter.
2. **~~⚠ FLAGGED RISK (Z80-core reset PC)~~ — VOID.** ADR 0018-A resolves ADR 0018 Decision 6 / OQ1 **in the
   negative**: apl2cpm3's NOP-slide-from-`$0000`-to-`$0100` cold-start is faithful and our `Z80Cpu.Reset()→PC=0`
   + slot-4 toggle already model it. **There is NO Z80-core change and NO owner sign-off needed.** Do NOT touch
   `Z80Cpu.Reset()`, `Machine.SetCoprocessorActive`, `SoftCardControlPort`, `SoftCardTranslation`, or
   `CoprocessorSpec` — they are all correct. The blocker was a disk-read sector-order bug, not a CPU bug.
3. **`CpmBootCycles` raised to 20 M** (from the 2.2 gate's 10 M) because CP/M-3's loader chain is longer
   (ADR 0018 OQ4). Tune on the first green run — if the boot settles earlier, lower it; if it needs more,
   confirm the boot completes within a reasonable budget (OQ4: no new timing risk expected, CP/M-3 is still a
   coarse-timed workload at clock ratio 2.0).
4. **40-col vs 80-col staging (OQ2):** the gate asserts the CP/M-3 console on the **40-col** page. If apl2cpm3's
   BIOS goes *straight* to 80-col (the Videx) without ever painting the 40-col page, this gate's `A>` assertion
   would not find it on `$0400` — in that case the 40-col milestone collapses into the 80-col headline (V80-3)
   and this gate is re-scoped to assert the early sign-on (pre-`icrt`) the disk paints to 40-col, OR deferred
   into V80-3 with a note. The live boot decides; the gate asserts whichever the disk actually does (no
   pre-assumption — ADR 0018 Decision 4). Record the finding in the PR body.
