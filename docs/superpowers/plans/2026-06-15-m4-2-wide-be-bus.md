# M4.2: The Wide Big-Endian Bus (`Read16/Read32/Write16/Write32` + `Endianness`, Foundation, Synthetically Proven)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended)
> or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax
> for tracking.

**Goal:** add wide **word (16-bit)** and **long (32-bit)** bus transactions plus an **`Endianness`** notion
to the `IAddressSpace` seam — big-endian for the 68000 — implemented on `AddressSpace`, with a 68000
odd-address (word-alignment) **detection** seam, and prove the whole wide-bus foundation **synthetically**
(BE round-trips, hi-byte-first writes, endianness correctness, odd-address detection, per-access
transaction granularity), all while keeping the 6502 + Z80 generated output **byte-identical** and
byte-only, and their full suites green. **No 68000 instruction executes** (decode/EA/ops are M4.3+); this
PR ships the wide bus + the synthetic proof only, mirroring the M4.1 "ship the foundation, no opcode goes
live" discipline.

**Architecture:** Per ADR 0003 Decision 2 (Option A — wide accessors on the seam, `Endianness` a bus
property NOT composed from a CPU-side convention), grow `IAddressSpace` with `Read16/Read32/Write16/Write32`
+ an `Endianness Endianness { get; }` property, all as **default interface methods** so the in-tree
`IAddressSpace` implementer that does NOT derive from `AddressSpace` (the test `TracingAddressSpace`)
keeps compiling untouched. `AddressSpace` gets a concrete wide path: a `using System.Buffers.Binary`
`BinaryPrimitives.Read/Write{UInt16,UInt32}{Big,Little}Endian`-style implementation that composes over the
existing `Read8`/`Write8` page-table path (so it inherits page-table resolution, MMIO callouts, ROM-ignore,
wrap-masking, and strict-mode for free), with `Endianness` defaulting to `LittleEndian` and selectable at
construction. The 68000 alignment-**detection** seam is a pure static helper `BusAlignment.IsMisaligned(addr,
width)` (no exception raised — the address-error EXCEPTION is M4.5). The `TracingAddressSpace` is upgraded
to record per-access **size** (`.b`/`.w`/`.l`) so the eventual M4.5 TomHarte trace gate has word-granular
transactions. The 6502/Z80 emit and the JIT fastmem IL are **untouched** — the wide methods are additive,
and the wide-bus JIT emit arm is M6 (ADR 0003 Decision 3).

**Tech Stack:** C# (.NET 10), `System.Buffers.Binary.BinaryPrimitives`, xUnit. The Roslyn source generator
(`CpuEmulator.Generators`) and the spec importer are **NOT touched** in M4.2 (this is a Core-bus PR, no
generated CPU code changes). The 68000 TomHarte gate (SingleStepTests/680x0) is **out of scope** for M4.2
(it arrives with the interpreter, M4.5).

## Scope

This PR ships the **bus FOUNDATION only**. Per ADR 0003 Decision 2 + the ADR 0004 §3 M4.2 boundary, M4.2
delivers the wide big-endian transactions the whole M4 arc needs for memory access, proven synthetically.

**IN scope:**

1. **Add `Read16/Read32/Write16/Write32` + `Endianness Endianness { get; }` to `IAddressSpace`** as
   **default interface methods** (Decision D1). `Read16`/`Write16` are ONE transaction (one word, two byte
   accesses composed by `Endianness`); `Read32`/`Write32` are **two** word transactions (high word first
   for big-endian). The defaults compose over `Read8`/`Write8` so any `IAddressSpace` implementer gets a
   correct wide path for free (and a little-endian default keeps existing consumers byte-identical).
2. **Implement the wide path concretely on `AddressSpace`** (Decision D2) — `Endianness` selectable at
   construction (default `LittleEndian`; the 68000 will construct `BigEndian` in M4.5), the wide methods
   composing over the existing `Read8`/`Write8` page path (inheriting page resolution, MMIO callouts,
   ROM-ignore, address wrap, strict-mode). Big-endian `Write16` writes the **high byte first**; big-endian
   `Write32` writes **4 bytes big-endian** (= two words, high word first).
3. **Add the `Endianness` enum** (`LittleEndian`, `BigEndian`) to `Core` (Decision D2).
4. **Add the odd-address / word-alignment DETECTION seam** (Decision D3): a pure static
   `BusAlignment.IsMisaligned(uint address, AccessWidth width)` — `true` iff `width != Byte && (address &
   1) != 0`. **M4.2 raises NO exception** — it provides the detection predicate only. The Address-Error
   EXCEPTION vectoring is deferred to the exception model (M4.5, per ADR 0004 Decision 3). Document
   exactly what M4.2 delivers (the predicate + the wide accessors) vs defers (the raise/vector).
5. **Upgrade `TracingAddressSpace`** (the test bus) to record each access with its `AccessWidth`
   (`.b`/`.w`/`.l`) and BE/LE flavour, so the eventual M4.5 mnemonic-keyed TomHarte trace gate can diff
   word-granular transactions (Decision D4). The 6502/Z80 trace tests, which assert byte accesses, stay
   green (a byte access records `AccessWidth.Byte`, the default).
6. **The synthetic proofs:** wide BE/LE read/write round-trips through a real `AddressSpace`; 16-bit writes
   are hi-byte-first under BE / lo-byte-first under LE; 32-bit writes lay 4 bytes big-endian (two words,
   high word first) under BE; word/long accesses straddling a page boundary compose correctly; wide reads
   from ROM and MMIO go through the same page path; `BusAlignment.IsMisaligned` is correct for every
   (address-parity × width); the `TracingAddressSpace` records the per-access size.

**OUT of scope (each is a later M4 PR — do NOT reach for it):**

- **The Address-Error EXCEPTION** (raising + vectoring through vector 3 on an odd-address word/long
  access, the bus-error extended stack frame) = **M4.5** (the exception/vector machinery, ADR 0004
  Decision 3). M4.2 ships the DETECTION predicate; the raise has no home until the exception model exists.
- **The wide-bus / 32-bit JIT emit arm** (a `BinaryPrimitives` wide load over the fastmem `byte[]` page

  accessors go through the **normal `AddressSpace` wide path** (composing over `Read8`/`Write8`), NOT

  wide-bus arm in the M4 arc.
- **The 68000 actually USING the wide bus** (the `M68000Cpu` partial calling `Read16`/`Write32` for opcode
  prefetch, EA dereference, stack push/pop, vector reads) = **M4.5** (the interpreter). M4.2 leaves the
  `M68000Cpu` byte-only `ReadBus`/`WriteBus` (from M4.1) UNCHANGED — the wide bus exists and is proven, but

- **Constructing the 68000's bus as `BigEndian`** = **M4.5** (when the `M68000Cpu` ctor / the TomHarte

- **`AccessWidth`-threaded MMIO semantics changes** — `IPeripheral.Read/Write` ALREADY take an

## Decisions (made for M4.2; the ADR fixed Option A but left the surface "the M4 bus PR's to settle")

ADR 0003 Decision 2 chose Option (A) and gave a **recommended surface** ("the final shape is the M4 bus
PR's to settle"). M4.2 is that PR. Each decision below settles a degree of freedom the ADR left open, so
the Builder does not re-litigate it and the Coordinator can veto before the run.

### D1 — The wide methods + `Endianness` land as DEFAULT INTERFACE METHODS on `IAddressSpace`

The ADR's illustrative surface (ADR 0003 Decision 2) declares `ushort Read16(uint)`, `uint Read32(uint)`,
`void Write16(uint, ushort)`, `void Write32(uint, uint)`, `Endianness Endianness { get; }` on
`IAddressSpace`. The open question: are these **abstract** (every implementer must write them) or
**default** (composed over `Read8`/`Write8` on the interface, overridable)?

**Decision: DEFAULT interface methods.** `IAddressSpace` provides a correct composing implementation of all
four wide methods (and `Endianness => Endianness.LittleEndian` as the default property), so:
- The **one in-tree `IAddressSpace` implementer that does NOT derive from `AddressSpace`** — the test
  `TracingAddressSpace` (`tests/CpuEmulator.Tests/Mos6502/TracingAddressSpace.cs`, confirmed: it
  `: IAddressSpace`, delegating to an inner space) — compiles **without forced edits** (it inherits the
  defaults; Task 6 then OVERRIDES them to record the size, by choice, not by compiler force).
- Any future test double or alternate bus gets a correct wide path for free.
- `AddressSpace` **overrides** the defaults with the concrete page-path implementation (Decision D2) — it
  has the page table, so it composes over its own `Read8`/`Write8` directly (the default's behaviour, but
  the override lets `AddressSpace` carry the construction-time `Endianness` field and is the obvious home).

**Why default, not abstract:** the ADR's whole Option-A thesis is "endianness is a bus property, and the
wide access composes over the byte path." That composition is **identical for every implementer** (it is
just byte ordering over `Read8`/`Write8`), so it belongs ON the interface as a default, not duplicated into
every implementer. Abstract methods would force `TracingAddressSpace` (and every future double) to
re-implement byte ordering — exactly the duplication the default eliminates. This is additive: existing
implementers gain four methods + a property they did not have, all with working bodies.

> **Confirmed reconciliation with ADR 0003.** The ADR says "The default implementations for a
> little-endian space may compose from `Read8`." This decision takes that literally: the interface-level
> defaults compose from `Read8`/`Write8`, `Endianness` defaults to `LittleEndian`. Fully consistent with
> the ADR; D1 only settles WHERE the default lives (on the interface, as a DIM).

### D2 — `AddressSpace` carries `Endianness` as a CONSTRUCTION-TIME field; the wide path uses `BinaryPrimitives`-style byte ordering over its own `Read8`/`Write8`

ADR 0003 Decision 2: "endianness a bus property"; "the big-endian path assembles high-byte-first." The open
question: is `Endianness` fixed at construction, or settable later?

**Decision: `Endianness` is a constructor parameter on `AddressSpace`, defaulting to `LittleEndian`,
immutable after construction** (a `get`-only property). A bus's byte order is a hardware property of the
board, fixed for the machine's life — there is no use case for flipping it at runtime, and immutability
keeps the wide path branch-predictable and lets the JIT (M6) treat it as a constant. The 68000's bus is
constructed `BigEndian` in M4.5; the 6502/Z80 buses keep the `LittleEndian` default (they never construct
with an explicit endianness, so their behaviour is byte-identical).

The wide read/write composes over `AddressSpace`'s own `Read8`/`Write8` so it inherits **all** the existing
semantics for free — page resolution, MMIO peripheral callouts, ROM-write-ignore, address-wrap masking,
and strict-mode throws — with NO duplication of the page-table walk. Concretely (illustrative; the literal
code is in Task 2):

```csharp
public ushort Read16(uint address) =>
    Endianness == Endianness.BigEndian
        ? (ushort)((Read8(address) << 8) | Read8(address + 1))
        : (ushort)(Read8(address) | (Read8(address + 1) << 8));
```

**Why compose over `Read8`/`Write8`, not a direct page-array read:** the ADR's J4 note ("the split is
generic; only the byte-only-ness was 6502-shaped") and the M4.2 OUT-of-scope line both say the
**fastmem/`BinaryPrimitives`-over-the-page-array** path is M6. M4.2's job is the CORRECT wide bus, not the
FAST one. Composing over `Read8`/`Write8` is correct by construction (it reuses the proven byte path,
including the cross-page case — a word at `0x00FF` reads byte `0x00FF` then byte `0x0100`, each resolving
through its own page entry) and is the "wide accessors go through the normal bus path first" the task scope
requires. A page-array fast path is a later optimization that must produce byte-identical results — proven
in M6 against this correct baseline.

> **Note on `BinaryPrimitives`:** the ADR names `BinaryPrimitives.Read{UInt16,UInt32}BigEndian` for the
> FASTMEM path (a span over the page array). M4.2 does NOT have a contiguous span (a wide access may
> straddle two pages with different backings), so the M4.2 wide path uses explicit `Read8`/`Write8`
> composition (the shift/or form above), NOT `BinaryPrimitives` over a span. `BinaryPrimitives` over the
> page `byte[]` is the M6 fastmem optimization. This is a deliberate, recorded divergence from the ADR's
> illustrative fastmem snippet — and it is CORRECT: the ADR's `BinaryPrimitives` line is explicitly about
> "the JIT fastmem wide path," which is M6, not M4.2.

### D3 — Odd-address handling: M4.2 ships a pure DETECTION predicate; the bus does NOT raise; the EXCEPTION is M4.5

ADR 0003 Decision 2: "the alignment check has one home (the bus, where the address and the access-width are
both known)." ADR 0004 Decision 3: "the address-error / alignment check has its home in the bus … and
raises the address-error path — [but] the raise [is] wired in M4.5"; "exception-capable ops are
`NeedsFallback` first … automatic for M4." So the BUS is the right HOME for the check, but the RAISE
depends on the exception/vector machinery (vector 3, the supervisor stack frame, mode switch) that does not
exist until M4.5.

**Decision: M4.2 provides the alignment DETECTION as a pure, side-effect-free static predicate
`BusAlignment.IsMisaligned(uint address, AccessWidth width)`** in `Core`, returning `true` iff the access
is wider than a byte AND the address is odd (`width != AccessWidth.Byte && (address & 1u) != 0`). M4.2 does
**NOT**:
- raise any exception from `Read16/Read32/Write16/Write32` (a misaligned wide access in M4.2 still reads/
  writes the bytes — the predicate is informational; the 68000 interpreter, M4.5, will consult the
  predicate BEFORE the access and vector instead);
- add any throw/vector path to `AddressSpace` (no `AddressErrorException` type — that is M4.5);
- change `Read8`/`Write8` (byte access is never misaligned; the predicate returns `false` for `Byte`).

**Why a free function, not a method on `IAddressSpace`:** alignment is a property of (address, width), not
of a particular bus instance — every bus has the identical rule (the 68000's even-alignment requirement is
the only one that matters, and it is universal). A static predicate is the minimal, testable home, has no
per-instance state, and the M4.5 interpreter can call it without a bus reference. Putting it on the
interface would imply per-bus alignment policy, which does not exist. (If M4.5 finds it wants the bus to
own a "raise on misalign" policy, it can add it then — but M4.2 keeps the predicate free and the bus
raise-free, matching "the EXCEPTION is M4.5.")

> **Flag for the Coordinator:** this means a misaligned `Read16` in M4.2 returns the (little- or big-endian
> composed) two bytes WITHOUT faulting. That is correct for M4.2 (no exception model exists) and harmless
> (nothing calls the wide bus at a misaligned address yet — the 68000 does not call it at all). The M4.5
> interpreter is responsible for checking `IsMisaligned` BEFORE a wide access and vectoring. M4.2 documents
> this contract on `BusAlignment` and in the wide-method XML docs. If the Coordinator prefers the bus to
> throw a placeholder on misalign NOW (so a stray misaligned access is loud), say so — the plan defaults to
> the ADR's "the raise is wired in M4.5" and keeps M4.2's bus non-throwing for wide accesses.

### D4 — `TracingAddressSpace` records per-access `AccessWidth`; the 6502/Z80 byte traces stay green

ADR 0003 Decision 2: "the test `TracingAddressSpace` … must now record `.b`/`.w`/`.l` transactions to diff
against the vectors." The open question: upgrade the EXISTING `TracingAddressSpace` (used by the 6502 trace
tests) or add a new one?

**Decision: upgrade the existing `TracingAddressSpace`** (`tests/CpuEmulator.Tests/Mos6502/
TracingAddressSpace.cs`) so each recorded `BusAccess` carries its `AccessWidth` (defaulting to `Byte` for
the existing `Read8`/`Write8` overrides), AND override the wide DIMs so a `Read16`/`Write32` records a
SINGLE entry tagged `Word`/`Long` (not the composed byte accesses). This is what the M4.5 TomHarte trace
gate needs: word-granular transactions with a size tag, matching the `["r", 4, 6, 3076, ".w", 1657]`
vector shape (ADR 0003 §1.4).
- The existing 6502 trace tests assert byte accesses (`R 0123=AB`); a `Read8` records `AccessWidth.Byte`,
  so those tests stay green **if** the `BusAccess` record's `ToString()` / equality is kept
  byte-compatible (Decision: add `Width` with a `Byte` default so existing `new BusAccess(addr, val,
  isRead)` call sites and assertions are unchanged — the `Width` field is appended with a default value).
- The wide overrides MUST NOT double-record: a `Read16` records ONE `Word` entry, then reads the two bytes
  via the inner space's `Read8` (which, because `inner` is the wrapped real `AddressSpace`, does NOT go
  back through the tracer — the tracer wraps the real space, the real space's `Read8` is plain). Confirm
  at recon (Task 0) that the tracer delegates to `inner.Read8`, so the byte reads inside a traced `Read16`
  do NOT re-enter `Trace`.

> **Recon caveat (R-trace, Task 0):** confirm the existing 6502 trace tests construct `TracingAddressSpace`
> with `new BusAccess(addr, val, isRead)` (positional, 3-arg) and assert on `Trace` entries. If any test
> matches on the FULL `BusAccess` value (including a future `Width`), appending `Width` with a `Byte`
> default keeps positional construction + value-equality byte-compatible (the appended optional field
> defaults to `Byte`, equal to what a byte access would record). Re-confirm the exact call sites at Task 0
> before editing the record.

### D5 — A wide access on an MMIO page calls the peripheral ONCE with the access width (not N byte callouts)

The wide path composes over `Read8`/`Write8`, and `AddressSpace.Read8` on an MMIO page calls
`page.Handler.Read(offset, AccessWidth.Byte)` (`AddressSpace.cs:83`). So a naive `Read16` over an MMIO page
would call the peripheral TWICE with `AccessWidth.Byte`. The open question: is that correct, or should a
wide MMIO access be ONE peripheral callout with `AccessWidth.Word`/`Long`?

**Decision: M4.2 composes over `Read8`/`Write8` UNIFORMLY — including the MMIO case — so a wide MMIO access
is N byte callouts each with `AccessWidth.Byte`.** Rationale: this is the **correct, conservative M4.2
behaviour** and keeps the wide path a pure composition (one code path, no MMIO special-case). The 68000's
TomHarte vectors are RAM-backed (the `ram` array is memory; there is no peripheral in the SingleStepTests
fixtures), so M4.2's synthetic proofs and the eventual M4.5 gate exercise the RAM path, where byte
composition is exactly right (two `Read8`s over RAM = the two bytes of the word). A real 68000 board with a
16-bit peripheral that wants a single `AccessWidth.Word` callout is a **device-modelling** concern for
whenever such a board exists — NOT a Core-bus concern for M4.2, and `IPeripheral.Read/Write` already carry
`AccessWidth` for that future. **Recording this as a known, bounded limitation** (a wide MMIO access is
byte-decomposed at the peripheral) keeps M4.2 minimal and correct for everything it must serve.

> **Flag for the Coordinator:** if you want wide MMIO accesses to be a SINGLE width-tagged peripheral
> callout in M4.2 (so a future 16-bit device sees `AccessWidth.Word`), that is a larger change — the wide
> path must branch on the page kind (memory → byte-compose; MMIO → single width callout; straddling
> memory/MMIO → ?), which pulls page-table internals into the wide path and adds the straddle ambiguity.
> The plan defaults to uniform byte composition (simplest correct thing; no peripheral in any current or
> M4.5 fixture). Revisit when a wide-bus peripheral actually exists.

    /// <summary>The byte order of this bus's multi-byte (word/long) transactions (ADR 0003 Decision 2).
    /// Default <see cref="Endianness.LittleEndian"/> (the 6502/Z80 order); the 68000's bus is
    /// <see cref="Endianness.BigEndian"/>. The wide accessors below assemble bytes per this.</summary>
    Endianness Endianness => Endianness.LittleEndian;

    /// <summary>Read one 16-bit word — ONE transaction (two byte accesses composed per
    /// <see cref="Endianness"/>). Big-endian: the high byte is at <paramref name="address"/>. The default
    /// composes over <see cref="Read8"/>; <see cref="AddressSpace"/> overrides with its page path. Each
    /// composed byte access masks its address independently (the bus wraps at the top of the space).
    /// NOTE (M4.2): a word/long access at an ODD address is misaligned on the 68000 (see
    /// <see cref="BusAlignment.IsMisaligned"/>); M4.2 does NOT fault here — the address-error EXCEPTION is
    /// the M4.5 exception model's job. The caller (the M4.5 interpreter) checks alignment BEFORE the
    /// access.</summary>
    ushort Read16(uint address) =>
        Endianness == Endianness.BigEndian
            ? (ushort)((Read8(address) << 8) | Read8(address + 1))
            : (ushort)(Read8(address) | (Read8(address + 1) << 8));

    /// <summary>Read one 32-bit long — TWO word transactions, HIGH WORD FIRST under big-endian
    /// (ADR 0003 §1.2). Composes over <see cref="Read16"/>.</summary>
    uint Read32(uint address) =>
        Endianness == Endianness.BigEndian
            ? ((uint)Read16(address) << 16) | Read16(address + 2)
            : (uint)Read16(address) | ((uint)Read16(address + 2) << 16);

    /// <summary>Write one 16-bit word — ONE transaction (two byte accesses composed per
    /// <see cref="Endianness"/>). Big-endian: the HIGH byte is written at <paramref name="address"/>
    /// (high-byte-first). See the M4.2 alignment note on <see cref="Read16"/>.</summary>
    void Write16(uint address, ushort value)
    {
        if (Endianness == Endianness.BigEndian)
        {
            Write8(address, (byte)(value >> 8));       // high byte at the lower address
            Write8(address + 1, (byte)value);
        }
        else
        {
            Write8(address, (byte)value);              // low byte at the lower address
            Write8(address + 1, (byte)(value >> 8));
        }
    }

    /// (ADR 0003 §1.2). Composes over <see cref="Write16"/>.</summary>
