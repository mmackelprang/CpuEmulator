# M3.4a: The Z80 Interpreter Comes Alive — the BASE Opcode Plane, TomHarte-Green

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** make the Z80 **EXECUTE** for the first time. M3.4a brings the **un-prefixed BASE opcode
plane** (the ~250 opcodes that need neither IX/IY nor the CB/ED prefixes) from the M3.3 *decode
skeleton* (698 rows, 13 emitted, the rest `// TODO`) to a **flag-correct, cycle-correct, running
interpreter** that passes its **TomHarte Z80 SingleStepTests vectors** for the base-plane opcodes.
This is the framework's **first execution of a non-6502 ISA** — the moment the M1/M2/M3.1–M3.3
abstractions stop being "a 6502 emulator with extra indirection" (ADR §1.1,
`docs/architecture/0001-z80-second-architecture.md:22-23`) and become a *framework* that runs two
genuinely different instruction sets.

To get there, M3.4a lands the framework's Z80 **register/flag MODEL**, the Z80 **register-shape
addressing modes**, the Z80 **base-plane micro-op vocabulary** (a flag-correct 8-bit ALU, INC/DEC,
16-bit ADD HL,rr, the LD matrix, PUSH/POP, EX/EXX, the full conditional+unconditional flow set, DAA,
SCF/CCF/CPL), and the **Z80 TomHarte harness**. Every framework change is **additive**: the 6502's
generated output stays byte-identical (the new AddrModes / Flags / micro-ops never appear in 6502
literals; `Mos6502Spec.cs` is untouched), and the full 6502 suite + `CPUEMULATOR_UAT=full` both-tier
sweep + Klaus stay green throughout.

**This is the largest, most consequential chunk of M3.** It is honestly scoped as the **FIRST of a
2–3 PR sub-arc** (M3.4a base plane → M3.4b CB/ED plane → M3.4c DD/FD/DDCB/FDCB plane), recommended in
§"The M3.4 sub-arc decomposition" below. M3.4a does **not** attempt the prefixed planes, the block
ops, the rotate/shift family, the bit group, the interrupt modes, or the Z80-through-the-JIT — each
is named in Scope with its later chunk.

**The honest one-liner for M3.4a's close-state:** the Z80 BASE plane runs and is TomHarte-green
(per-instruction registers incl. the undocumented F.X/F.Y bits, memory, AND per-cycle bus trace);
the prefixed planes remain `// TODO` skeleton; the Z80 still runs **interpreter-only** (the JIT is
M3.5). "TomHarte-green" is asserted only over the **covered base-plane opcode set** documented in
§"Ground truth H", not the whole 256-byte base page (some base bytes are CB/ED/DD/FD prefixes or
defer to later chunks — enumerated honestly).

**PR:** branch `feat/m3-z80-core` (base `main`, head `5eea933` — the M3.3 extraction merge, PR #19;
**~1526 tests green** is the baseline — confirm the EXACT number at Task 0 and record it). This plan
file is a preparatory doc commit on that branch; the implementation tasks follow.

## Scope

**IN scope (the base plane comes alive, end to end):**

1. **The Z80 register/flag MODEL (framework, additive).**
   - The Z80 **register pairs with bidirectional aliasing** — `A F B C D E H L` as 8-bit storage with
     `AF BC DE HL` as 16-bit **generated computed views** (read `BC` = `(B<<8)|C`; write `BC`
     decomposes back to `B`/`C`), per ADR Decision 3 option (A) (`0001-…:258-265`) and the 8086-brief
     bidirectional-aliasing pattern. The M3.3 register *declarations* already shipped (the 22 halves +
     16-bit registers, `z80-semantics.json:5-28`, `Z80Spec.cs:21-45`); M3.4a adds the **pair-view
     synthesis** the DSL did not yet express (the recorded M3.3 gap, `m3d-…:550-558`).
   - The Z80 **flag register** `S(7) Z(6) Y(5) H(4) X(3) P/V(2) N(1) C(0)` — extend the `Flag` enum,
     the generator's `FlagBit` map + `s_flagMembers` mirror, and a **composable flag-micro-op family**
     (`SetSZ`/`SetHalfCarry`/`SetParity`/`SetOverflow`/`SetXY`/`SetAddSub`) designed GENERAL so the
     8086 reuses them (ADR Decision 3, `0001-…:301-308`; the 8086-brief flagged this). The
     **undocumented X/Y flags** (bits 3/5, copied from results) are modeled — TomHarte checks them
     (ADR §1.3, `0001-…:84-85`; risk #4, `0001-…:697-701`).

2. **The Z80 register-shape AddrModes (carry-forward 2, NEEDED NOW).** Add to the `AddrMode` enum +
   the parser's `s_addrModes` mirror + the parser class/mode matrix + the emitter + the importer's
   `SupportedModes`: **`Register`** (`LD r,r'`, `OR r`), **`RegisterIndirect`** (`(HL)`, `(BC)`,
   `(DE)`), **`ImmediateExtended`** (16-bit `LD rr,nn`), **`ExtendedAddress`** (`(nn)` 16-bit absolute,
   byte and word), **`RelativeJump`** (`JR`/`DJNZ`). The M3.3 skeleton's TODO(mode) rows already name
   these (`Z80Spec.cs:70-73,182-245,118-181`). **`Indexed`** (`(IX+d)`) and **`Bit`** (CB plane)
   **DEFER** to M3.4c / M3.4b respectively — they are in the M3.3 dataset as TODO but M3.4a does NOT
   make them executable (said plainly in NOT-in-scope).

3. **The base-plane micro-op vocabulary (the bulk of the work).** New `Op` records + `Spec` factories
   + parser signatures/arities + parser class/mode entries + emitter bodies + importer `FactoryArity`,
   for:
   - **Flag-correct 8-bit ALU** — `ADD/ADC/SUB/SBC/AND/OR/XOR/CP A,(r|(HL)|n)` with the Z80 H / P-V /
     N flag rules (NOT the 6502's N/Z/C/V). The M3.3 skeleton mis-maps these to the 6502 `Adc`/`Sbc`/…
     factories (covered-for-decode-shape, **wrong-for-flags** — `m3d-…:564-570`); M3.4a replaces them
     with flag-correct Z80 ALU micro-ops over the `Register`/`RegisterIndirect`/`Immediate` modes.
   - **INC/DEC r** (8-bit) with H and P/V (overflow), N set per direction, **C preserved** (a Z80 rule
     the 6502 INC/DEC has no analog for).
   - **16-bit ALU** — `ADD HL,rr` (sets H/C/N from the 16-bit add; leaves S/Z/P-V; sets X/Y from the
     high byte) and `INC rr`/`DEC rr` (which set **no flags** — the Z80 quirk the generator must not
     "helpfully" add, `0001-…:347`).
   - **LD forms** — the register-to-register matrix (`LD r,r'`), immediate (`LD r,n`), `(HL)` indirect
     (`LD r,(HL)` / `LD (HL),r` / `LD (HL),n`), `(BC)`/`(DE)` indirect (`LD A,(BC)` etc.), the 16-bit
     immediate loads (`LD rr,nn`), `(nn)` extended loads (`LD (nn),HL` / `LD HL,(nn)` / `LD (nn),A` /
     `LD A,(nn)`), and `LD SP,HL`.
   - **register-pair PUSH/POP** (`PUSH BC`/`POP BC`/… incl. `AF`) — a 16-bit-pair stack op (today's
     `Push`/`Pull` are 8-bit-register).
   - **EX/EXX** — `EX DE,HL`, `EX AF,AF'`, `EXX` (the alternate-set wholesale swap), `EX (SP),HL`
     (a memory exchange).
   - **flow** — `JP nn`, `JP cc,nn`, `JP (HL)`, `JR d`, `JR cc,d`, `DJNZ d`, `CALL nn`, `CALL cc,nn`,
     `RET`, `RET cc`, `RST n`. The Z80 conditionally **calls** and **returns** (the 6502 only branches
     conditionally — ADR Decision 4, `0001-…:364-366`).
   - **misc** — `DAA` (needs H and N), `CPL`, `SCF`, `CCF`, and `NOP`/`HALT`/`DI`/`EI` (NOP and HALT
     already covered; DI/EI set the IFF latches — a small partial hook).
   - Complete the **`z80-semantics.json` base-plane entries** so the importer regenerates `Z80Spec.cs`
     with these as real `Insn` rows (not TODO). The regenerated spec is committed for review.

4. **The Z80 TomHarte harness + base-plane green.** A `get-test-vectors` **Z80 variant** that fetches
   the `SingleStepTests/z80` vectors (a DIFFERENT repo from the 6502's `ProcessorTests` — see Ground
   truth H), a Z80 **TomHarte loader** (the Z80 JSON schema differs: packed `af_/bc_/de_/hl_` alt
   pairs, `wz`/`q`/`iff1`/`iff2`, a separate `ports` array, `m`/`i` cycle signals), a Z80 **runner**
   (set state via `SetRegister` introspection incl. the F.X/F.Y bits, `Step()` one instruction, diff
   registers + memory + per-cycle bus trace), wired the same way as the 6502 harness with the same
   **skip-when-absent** discipline (`TomHarteVectors.cs:30-38`). The base-plane covered opcode set the
   run asserts is documented (Ground truth H).

**NOT in scope (stated so an implementer does not reach for it — each is a later sub-arc PR or
milestone):**

- **The CB plane (M3.4b).** Bit/rotate/shift: `BIT/SET/RES n,r`, `RLC/RRC/RL/RR/SLA/SRA/SRL`, and the
  A-specific `RLCA/RRCA/RLA/RRA` (which set flags DIFFERENTLY from the CB forms) + `RLD/RRD`. The
  bit-index operand needs a new `Op` operand slot (ADR Decision 4, `0001-…:352-353`). The base-plane
  `RLCA/RRCA/RLA/RRA` (opcodes 0x07/0x0F/0x17/0x1F) **defer to M3.4b** with the rest of the
  rotate/shift family (they share the rotate emit arm) — recorded honestly in Ground truth H, not
  silently absorbed.
- **The ED plane (M3.4b).** Block ops `LDIR/LDDR/CPIR/CPDR/INIR/OTIR/…` (self-repeating — a
  one-instruction loop), 16-bit `ADC/SBC HL,rr`, `IM 0/1/2`, `I`/`R` access (`LD A,I`/`LD A,R`),
  `NEG`, `RETI`/`RETN`, `RLD`/`RRD`, the `(C)`-indexed I/O (`IN r,(C)`/`OUT (C),r`).
- **The DD/FD/DDCB/FDCB planes (M3.4c).** IX/IY indexed `(IX+d)`/`(IY+d)` EA computation, AND the
  **two-deep compound-prefix decoder extension** (`DD CB dd op` — displacement BEFORE the opcode) —
  the recorded M3.3 enumerated finding (the shipped single-byte `PrefixByte`/`Insn` cannot express
  the two-deep prefix; `m3d-…:1176`). **DEFER the decoder extension to the DD/FD PR** per the brief.
  M3.4a's `DecodeStructure` adds CB/DD/FD prefix BYTES only insofar as the base plane's decode walk
  must SKIP into them (so 0xCB/0xED/0xDD/0xFD are recognized as prefixes that the base plane does not
  yet execute) — but the indexed-EA and compound-prefix MECHANISM is M3.4c.
- **Interrupt servicing (IM 0/1/2 + NMI + IFF1/IFF2).** ADR Decision 5 (`0001-…:402-447`). **The base
  plane may not need it for TomHarte single-instruction vectors** — each vector runs exactly one
  instruction from a given state with no interrupt asserted (`Mos6502TomHarteTests.cs:36`,
  one `Step()`). M3.4a implements `DI`/`EI` (they set IFF1/IFF2 latches, observable in the final
  state's `iff1`/`iff2` fields) but does NOT implement interrupt ACKNOWLEDGE / vectoring — that is
  M3.4b (it lands with `IM`/`I`/`R`). Scoped honestly: the harness asserts `iff1`/`iff2` for DI/EI
  vectors; it does not exercise an asserted INT line.
- **The Z80 through the JIT (M3.5).** `BlockCompiler`/`BlockDelegate`/`JittedCpu` stay typed to
  `Mos6502Cpu` (J1, `0001-…:505`); the Z80 runs interpreter-only. The Z80 JIT + the genericity
  findings (J1/J2/J3/J5/J9/J10) are M3.5.
- **ZEXALL/ZEXDOC.** The integration-tier Z80 exerciser (the 6502-Klaus analog, `0001-…:488`) lands
  with the full instruction set — realistically M3.4c close or a dedicated integration PR. M3.4a's
  gate is TomHarte base-plane per-cycle; ZEXALL needs CB/ED/DD/FD to run a real program.
- **Any 6502 change.** The 6502 spec, dataset, semantics, generated output, and tests stay UNTOUCHED
  and green. Every framework change (AddrModes / Flags / micro-ops) is STRICTLY ADDITIVE — the new
  vocabulary never appears in 6502 literals, so `Mos6502Spec.cs` and the generated `Mos6502Cpu`
  output are byte-identical (the pure-additivity invariant, §"Ground truth I").

**The M3.4 sub-arc decomposition (the recommendation the brief asks for):**

| PR | Plane(s) | Headline new work | Depends on | Est. rows made-live |
|---|---|---|---|---|
| **M3.4a** *(this plan)* | BASE (un-prefixed) | reg/flag MODEL + pair aliasing; 5 register-shape AddrModes; flag-correct 8-bit ALU + INC/DEC + ADD HL,rr + LD matrix + PUSH/POP + EX/EXX + full flow + DAA/SCF/CCF/CPL; the Z80 TomHarte harness | M3.3 (head `5eea933`) | ~190–210 base-plane rows (derived in §"Ground truth A") |
| **M3.4b** | CB + ED | the bit-index operand model; rotate/shift family (incl. base-plane RLCA/RRCA/RLA/RRA); BIT/SET/RES; block ops (self-repeat); 16-bit ADC/SBC HL,rr; IM 0/1/2 + NMI + IFF + interrupt ACK; I/R; NEG; RETI/RETN; RLD/RRD; (C)-indexed I/O | M3.4a | ~248 CB + ~80 ED |
| **M3.4c** | DD + FD + DDCB + FDCB | the `(IX+d)`/`(IY+d)` indexed EA; **the two-deep compound-prefix decoder extension** (the M3.3 enumerated finding); the DD/FD re-interpretation of HL→IX/IY | M3.4b | ~100 DD + ~100 FD + ~248 DDCB + ~248 FDCB (documented subset) |
| *(M3.5)* | — | Z80 through the JIT + the Decision-7 genericity findings; ZEXALL/ZEXDOC | M3.4c | — |

**Why this cut and not another.** The base plane is the only plane that needs **no new decode
machinery** — it is single-byte-keyed, which the shipped M3.1b decoder already handles (the 6502's
degenerate walk). It is also the only plane that is *self-contained*: every base-plane op's semantics
are expressible without the bit-index operand (CB), the block-op self-repeat (ED), or the indexed-EA
+ compound-prefix (DD/FD). Splitting CB/ED off (rather than bundling them as ADR Decision 8 originally
mused, `0001-…:561`) is the honest cut because **the bit-index operand and the block-op self-repeat
are each a genuine new operand/control-flow shape** that would balloon M3.4a; they earn their own PR.
M3.4c is last because it depends on M3.4b's CB plane (DDCB applies CB ops to `(IX+d)`) AND carries the
decoder extension, the single largest decode change remaining.

**Dependencies:** M3.4a → M3.4b → M3.4c → M3.5. Within M3.4a, the tasks are dependency-ordered (the
flag model and AddrModes before the micro-ops that use them; the harness last so it gates real green).

**Exact mode distribution of the 248-row target** (the verified counts the new-AddrMode work must

> **The `ADD Register` conflation — a real finding the emitter must resolve.** The M3.3 dataset tags
> BOTH `ADD HL,rr` (0x09/0x19/0x29/0x39 — 16-bit) AND `ADD A,r` (0x80–0x87 — 8-bit) with
> `mode == "Register"` (the dataset filter shows all 11 under `ADD`/`Register`). These are two
> different micro-ops (16-bit `Add16` vs 8-bit flag-correct ALU) sharing one mode tag. M3.4a's
> semantics map disambiguates by the operand the dataset encodes (the `source` field / the opcode
> range), authoring `ADD HL,rr` → `Add16(...)` and `ADD A,r` → the 8-bit ALU op. **Recorded: this is
> the one place the M3.3 dataset's mode tagging is coarser than the micro-op vocabulary needs; M3.4a
> resolves it in the semantics map + a parser distinction, NOT by re-extracting the dataset.** (If the
> dataset row's operand cannot be disambiguated cleanly, that is a Task-N finding — surface it, do not
> guess.)

### What M3.4a does NOT make live in the base plane (honest, enumerated)

- **RLCA/RRCA/RLA/RRA** (4 rows) → M3.4b (rotate family).
- The base bytes **0xCB / 0xED / 0xDD / 0xFD** are PREFIXES, not base-plane instructions — they are
  NOT in the 252 base rows (the dataset keys them under their planes). M3.4a's decode walk must
  recognize them as prefixes that route OUT of the base plane (to TODO planes), so a TomHarte vector
  whose first byte is a prefix is a LATER-plane vector and is excluded from the M3.4a covered set.
- `IN A,(n)` / `OUT (n),A` (2 rows, `IoPortImmediate`) are already emitted (M3.2 `PortIn`/`PortOut`,
  `Z80Spec.cs:265-266`) — M3.4a keeps them and the harness asserts them, but they are not NEW work.

### The new-vocabulary list (what M3.4a adds to the framework)

**New AddrModes (5):** `Register`, `RegisterIndirect`, `ImmediateExtended`, `ExtendedAddress`,
`RelativeJump`. *(`Indexed` and `Bit` are dataset-present but DEFERRED — M3.4c/M3.4b.)*

**New Flags (5 enum members + a re-layout):** add `S H P N Y X` to the `Flag` enum at the Z80 bit
positions (`S=7, Z=6, Y=5, H=4, X=3, P=2, N=1, C=0`) — `Z` and `C` already exist but at the 6502 bit
positions, so this is a **per-spec flag-bit map**, not a single global enum re-number (Ground truth B
explains how the generator keys flag bits per-spec so the 6502's `C=0,Z=1,…` is untouched).

**New flag micro-ops (6, composable + general):** `SetSZ(reg)`, `SetHalfCarry(...)`, `SetParity(reg)`,
`SetOverflow(...)`, `SetXY(reg)`, `SetAddSub(bool)` — designed so the 8086 reuses `SetSZ`/`SetParity`/
`SetOverflow` (ADR `0001-…:301-308`).

**New instruction micro-ops (the base-plane vocabulary):**
- 8-bit ALU (flag-correct Z80): `Add8`, `Adc8`, `Sub8`, `Sbc8`, `And8`, `Or8`, `Xor8`, `Cp8` *(named
  with the `8` suffix to coexist with the 6502 `Adc`/`Sbc`/… without colliding — Ground truth E
  records the naming).*
- 8-bit `IncReg`/`DecReg` (Z80 flag rules: H, P/V overflow, N per direction, **C preserved**).
- 16-bit: `Add16(target, source)` (`ADD HL,rr`), `Inc16(target)` / `Dec16(target)` (NO flags).
- LD: `Load16`/`Store16` (the `(nn)` word + the 16-bit-immediate forms); the 8-bit `(HL)`/`(BC)`/
  `(DE)` indirect LD reuses the new `RegisterIndirect` mode with `Load`/`Store`-shaped ops over the
  pair-EA (Ground truth E details which are new ops vs new-mode-over-existing-op).
- Pair stack: `Push16(pair)` / `Pop16(pair)`.
- Exchange: `ExDeHl`, `ExAfAf`, `Exx`, `ExSpHl`.
- Flow: `RelJump` (`JR`), `RelJumpIf(cc)` (`JR cc`), `Djnz`, `Call`, `CallIf(cc)`, `RetCc(cc)`,
  `Rst(vec)`, `JumpIf(cc)` (`JP cc`); `JP nn` reuses the existing `Jump`; `JP (HL)` is a
  `RegisterIndirect` jump; `RET` reuses `Rts`; `CALL nn` reuses `Jsr`.
- Misc: `Daa`, `Cpl`, `Scf`, `Ccf`; `Di`/`Ei` (partial latch hooks).

The exact factory/Op/parser-signature/emitter mapping is in Ground truth E.

## Ground truth A — the Z80 register/flag model + the bidirectional pair-aliasing contract

### A.1 What already shipped (M3.3) vs what M3.4a adds

M3.3 declared the 22 registers as DATA (`z80-semantics.json:5-28`), and the M3.1a data-driven register
file emits them as fields + `GetRegister`/`SetRegister` arms (`CpuEmitter.cs:60-88`): 8-bit registers
become `public byte A;` etc., 16-bit become `public ushort IX;`. So `A F B C D E H L A_ F_ … I R` are
`byte` fields and `IX IY SP PC` are `ushort` fields TODAY. **What is missing is the PAIR VIEW** — the
ability to name `BC`/`DE`/`HL`/`AF` as 16-bit operands and have reads/writes alias the two 8-bit
halves bidirectionally. This is the recorded M3.3 gap (`m3d-…:550-558`): "the pair-view synthesis is
M3.4 (it needs the `RegisterDef` pair-relationship the DSL does not yet express)."

### A.2 The bidirectional-aliasing contract (the 8086-brief pattern)

A register pair `BC` is **not stored**; it is a **computed accessor pair** over the two declared
8-bit halves `B` (high) and `C` (low):

```
read  BC  ≡  (ushort)((B << 8) | C)
write BC = v  ≡  { B = (byte)(v >> 8); C = (byte)v; }
```

The same for `DE`=(D,E), `HL`=(H,L), `AF`=(A,F). The alternate set pairs `AF' BC' DE' HL'` alias
`(A_,F_) (B_,C_) (D_,E_) (H_,L_)` identically. **Bidirectional** = a write to `C` then a read of `BC`
reflects it (no stale copy), and a write to `BC` then a read of `B` reflects the high byte — because
there is only ONE storage (the halves) and the pair is a pure view. This is the 8086-brief's
`B/C ⊂ BC` contract: the halves are storage, the pair is a generated view, so 8-bit ops on `C` and
16-bit ops on `BC` cannot drift (ADR Decision 3 option (A), `0001-…:258-265`).

### A.3 How the pair view is expressed (the DSL + generator delta)

**The DSL surface (`RegisterDef`):** add an optional pair-relationship carrier so a spec can declare
a 16-bit view over two 8-bit halves. The cleanest minimal shape (additive — the 6502 declares none):

```csharp
// RegisterDef.cs — NEW optional pair carriers (default null ⇒ 6502 shape, byte-identical):
public sealed record RegisterDef(
    string Name, int Bits, RegisterRole Role = RegisterRole.General,
    string? HighHalf = null,    // NEW (M3.4a): for a 16-bit VIEW register, the 8-bit high-half name
    string? LowHalf  = null);   // NEW (M3.4a): the 8-bit low-half name
// A pair view: new("BC", 16, HighHalf: "B", LowHalf: "C") — declares BC as a VIEW, not storage.
```

A pair-view `RegisterDef` has `Bits == 16` and BOTH `HighHalf`/`LowHalf` naming declared 8-bit
registers. The generator (CpuEmitter):
- Does **NOT** emit a backing field for a pair view (it is computed); instead emits a computed
  property: `public ushort BC { get => (ushort)((B << 8) | C); set { B = (byte)(value >> 8); C =
  (byte)value; } }`.
- The `GetRegister`/`SetRegister` arms (`CpuEmitter.cs:71-88`) route `"BC"` through the property (so
  introspection — and the TomHarte runner's `SetRegister("BC", …)` if it uses pair-granular set —
  works).
- A micro-op naming `BC` (e.g. `Push16("BC")`, `Add16("HL","BC")`, `Load16("HL", …)`) reads/writes
  the property; the parser's CPUGEN008 register-name gate (`SpecParser.cs:220`, the spec's own
  Registers table) accepts `BC` because it is a declared `RegisterDef`.

**The parser delta (`SpecParser.ParseRegisters`, `:237-279`):** accept the 4th/5th constructor args
(`HighHalf`/`LowHalf`); validate that a register with them set has `Bits == 16` and that both halves
name already-declared 8-bit registers (a new CPUGEN diagnostic — `CPUGENxxx: pair-view halves must
name declared 8-bit registers`). The 6502 spec uses neither arg, so its parse is byte-identical.

**The semantics-map / importer delta:** `z80-semantics.json` adds the pair-view registers to its
`registers` array (the 4 main + 4 alternate pairs):

```jsonc
// added to z80-semantics.json "registers" (the HighHalf/LowHalf views):
{ "name": "AF", "bits": 16, "highHalf": "A", "lowHalf": "F" },
{ "name": "BC", "bits": 16, "highHalf": "B", "lowHalf": "C" },
{ "name": "DE", "bits": 16, "highHalf": "D", "lowHalf": "E" },
{ "name": "HL", "bits": 16, "highHalf": "H", "lowHalf": "L" },
{ "name": "AF_", "bits": 16, "highHalf": "A_", "lowHalf": "F_" },
{ "name": "BC_", "bits": 16, "highHalf": "B_", "lowHalf": "C_" },
{ "name": "DE_", "bits": 16, "highHalf": "D_", "lowHalf": "E_" },
{ "name": "HL_", "bits": 16, "highHalf": "H_", "lowHalf": "L_" }
```

`SpecFileEmitter` emits these as `new("BC", 16, HighHalf: "B", LowHalf: "C")` rows in the regenerated
`Z80Spec.cs`. *(Recorded: the importer's register-emission `:92-105` grows the optional-arg emission;
the 6502 register emission is unchanged because the 6502 declares no halves.)*

> **Why pairs are VIEWS, not stored 16-bit registers (the genericity reason).** If `BC` were stored
> as a `ushort` and `B`/`C` were views, then `EXX` (the alternate-set swap) would have to swap eight
> 16-bit stores AND keep the half-views consistent, and `LD B,n` would have to read-modify-write a
> 16-bit store. Modeling the halves as storage makes `EXX` a swap of the eight `byte` fields (clean)
> and `LD B,n` a plain field write (clean). This matches the silicon: the halves ARE the registers
> (ADR `0001-…:262-263`). It also keeps `F`'s 8-bit flag manipulation first-class (the `Status` role
> is an 8-bit register, `z80-semantics.json:7`).

### A.4 The Z80 flag word (the model)

The Z80 `F` register layout (bit 7 → 0): `S Z Y H X P/V N C`.

| Bit | Flag | Meaning | Set by (base plane) |
|---|---|---|---|
| 7 | **S** (sign) | copy of result bit 7 | 8-bit ALU, INC/DEC, DAA |
| 6 | **Z** (zero) | result == 0 | 8-bit ALU, INC/DEC, DAA |
| 5 | **Y** (undoc) | copy of result bit 5 | 8-bit ALU, INC/DEC, DAA, SCF/CCF (from A) |
| 4 | **H** (half-carry) | carry out of bit 3 | 8-bit ALU, INC/DEC, DAA, ADD HL (from bit 11) |
| 3 | **X** (undoc) | copy of result bit 3 | 8-bit ALU, INC/DEC, DAA, SCF/CCF (from A) |
| 2 | **P/V** (parity/overflow) | parity for logic; overflow for arith | 8-bit ALU (overflow for ADD/SUB; parity for AND/OR/XOR), INC/DEC (overflow at 0x7F/0x80) |
| 1 | **N** (add/subtract) | 0 after add, 1 after subtract | every ALU/INC/DEC (drives DAA) |
| 0 | **C** (carry) | carry/borrow | ADD/ADC/SUB/SBC/CP, ADD HL, DAA, SCF/CCF |

The **undocumented X (bit 3) and Y (bit 5)** are copies of the corresponding result bits (or, for
SCF/CCF, of register `A` — a documented Z80 quirk TomHarte's `q` field tracks). M3.4a models them
because the TomHarte vectors check the full `f` byte (Ground truth G).

## Ground truth B — the per-spec flag-bit map (how the Z80 flag layout coexists with the 6502's)

**The problem.** The `Flag` enum bit positions are the 6502's: `C=0, Z=1, I=2, D=3, V=6, N=7`
(`Flag.cs:6-13`). The generator's `FlagBit` map mirrors them (`CpuEmitter.cs:563-572`) and
`s_flagMembers` mirrors the member NAMES (`SpecParser.cs:91-94`). The Z80 layout is
`C=0, N=1, P=2, X=3, H=4, Y=5, Z=6, S=7` — **`Z` is bit 1 on the 6502 but bit 6 on the Z80**, and
`V`/`P` and `N`/`H` collide on bit positions. A single global enum re-number would BREAK the 6502.

**The model: flag identity + bit position are per-spec, not a global enum.** The `Flag` enum stays a
NAME vocabulary; the **bit position is resolved per-spec** the same way M3.1a made register identity
per-spec (the recorded M3.1a precedent: "register identity is no longer a fixed enum,"
`SpecParser.cs:25-28`). Concretely:

- **`Flag` enum (`Flag.cs`)** grows the Z80 names as members: add `S, H, P, N, Y, X` (keeping the
  existing `C Z I D V N`). But the enum's NUMERIC VALUE stops being load-bearing for non-6502 specs —
  it remains the 6502's bit map for backward compatibility (the 6502 emitter reads
  `(int)Flag.C == 0`), and a new per-spec **flag-layout table** carries the Z80 bit positions.
- **A spec declares its flag layout** (additive — the 6502 declares none, falling back to the enum's
  6502 values). The cleanest minimal shape: an optional `FlagLayout` on the spec (a `Status`-register
  companion), or — preferred, since it parallels the register table — a per-`Flag` bit map the spec's
  Registers/semantics declare. **Recommendation:** carry the flag layout in the spec as a declared
  table the generator parses, analogous to `DecodeStructure`:

```csharp
// NEW (M3.4a, additive): a spec MAY declare its status-flag bit layout. ABSENT ⇒ the 6502 default
// (Flag enum values). The Z80 declares S=7..C=0. The generator keys FlagBit off THIS when present.
public static readonly FlagLayout Flags = new(
    [ new("S", 7), new("Z", 6), new("Y", 5), new("H", 4),
      new("X", 3), new("P", 2), new("N", 1), new("C", 0) ]);
public sealed record FlagLayout(FlagBitDef[] Bits);
public sealed record FlagBitDef(string Name, int Bit);
```

- **The generator (`CpuEmitter.FlagBit`, `SpecParser.s_flagMembers`)** becomes per-spec: when the spec
  declares a `FlagLayout`, `FlagBit("Z")` returns the spec's bit (6 for the Z80); absent, it returns
  the enum value (1 for the 6502). `s_flagMembers` grows to include the Z80 names so `SetFlag(Flag.H,
  …)` parses. **The 6502 path is byte-identical** — no `FlagLayout` declared ⇒ the enum values ⇒
  `0x7D` masks etc. unchanged.

> **Why a per-spec flag layout, not a second enum.** The flag-micro-op family (Ground truth C) emits
> bit masks (`1 << FlagBit(name)`). If the bit position were a fixed enum value, the Z80's `Z=6` would
> require either re-numbering the enum (breaks 6502) or a second `Z80Flag` enum (a parallel vocabulary
> the generator would have to branch on — the exact "secretly per-CPU" smell M3 exists to kill, ADR
> §1.1). Making the bit map per-spec DATA is the same move M3.1a made for registers and M3.1b for
> decode: identity is a name, layout is spec data. The 8086 (which has its own flag layout —
> `CF/PF/AF/ZF/SF/OF/…` at yet other bits) reuses this seam unchanged. **This is a genuine `Core` +
> generator change, enumerated and justified per §10.**

**The 6502-additivity proof for this change:** the 6502 spec declares no `FlagLayout`; `FlagBit`
falls back to the `Flag` enum's 6502 values; every 6502 flag mask (`0x7D`, `0x3C`, the ADC/SBC arms
`CpuEmitter.cs:660-742`) is emitted from the same fallback values it uses today; `Mos6502Spec.cs` is
unchanged (it never names `S/H/P/N/Y/X`). The new enum members are additive (adding members to an
enum does not change existing members' values). Pinned by `RegeneratedSpecTests` + the
generated-6502-byte-identical assertion (Ground truth I).

## Ground truth C — the composable flag-micro-op family (general, 8086-reusable)

The 6502 has ONE flag-setting micro-op, `SetNZ` (`Op.cs:12`, emitted `CpuEmitter.cs:411-418` as the
`0x7D` mask). The Z80's flag-setting is per-instruction-family and far richer (ADR Decision 3,
`0001-…:301-308`). Rather than a monolithic `SetZ80Flags`, M3.4a adds a **composable family** the
emitter combines per instruction, designed GENERAL so the 8086 reuses them:

| Micro-op | Factory | Arg(s) | Emits (into `F`, the Status register, using per-spec `FlagBit`) |
|---|---|---|---|
| `SetSZ(reg)` | `SetSZ("A")` | result reg | S = bit7 of reg; Z = (reg == 0) |
| `SetHalfCarry(...)` | (emitted inline by ALU arms) | the nibble-carry expr | H = carry/borrow out of bit 3 |
| `SetParity(reg)` | `SetParity("A")` | result reg | P/V = even parity of reg (used by logic ops, `LD A,I/R`) |
| `SetOverflow(...)` | (emitted inline by ALU arms) | operands+result | P/V = signed overflow (used by ADD/SUB/INC/DEC) |
| `SetXY(reg)` | `SetXY("A")` | result reg | X = bit3 of reg; Y = bit5 of reg (the undocumented copies) |
| `SetAddSub(bool)` | `SetAddSub(false/true)` | N value | N = 0 (add) or 1 (subtract) |

**The practical emission shape.** Most Z80 ALU/INC/DEC ops set MANY flags at once from a single
result+carry computation, so the EMITTER computes them inline in the op body (the half-carry and
overflow exprs need the operands, not just the result). The `SetSZ`/`SetParity`/`SetXY`/`SetAddSub`
**factories** exist for (a) the cases where they compose cleanly (`SCF` sets only C + X/Y from A;
`CCF` toggles C, sets H from old C, X/Y from A) and (b) the 8086 reuse (the 8086's `SF/ZF/PF/OF` map
1:1 to `SetSZ`/`SetParity`/`SetOverflow`). The H and overflow exprs are **inline emit helpers** the
ALU arm writes (like the 6502's ADC arm inlines its V/C computation, `CpuEmitter.cs:660-677`), not
standalone micro-ops — because they consume the pre-operation operand values the op body holds.

**Why `SetSZ`/`SetParity`/`SetXY`/`SetAddSub` are real factories (not just inline) — the genericity
payoff.** The 8086 brief flagged designing these GENERAL. Modeling `SetSZ`/`SetParity`/`SetOverflow`
as named, composable micro-ops means the 8086's spec authors `[Add8(...), SetSZ("AL"),
SetParity("AL"), SetOverflow(...)]` and reuses the SAME emitter arms — the flag layer becomes a
vocabulary, not a Z80 transliteration (ADR §3, the flag model "stops being one `SetNZ` convention").
M3.4a proves the vocabulary by using it for the Z80; the 8086 (M5) proves the reuse.

> **Recorded scope line: the H/overflow EXPRESSIONS are emitted inline by the ALU arms; the
> `Set*` FACTORIES cover the composable/standalone cases.** This is a deliberate design choice, not an
> oversight — a `SetHalfCarry()` standalone micro-op would have no operands to compute H from (they
> live in the op body), so the half-carry is an emit helper the ALU arm calls. The factory family
> covers what genuinely composes. The synthetic-flag generator test (Task 2) asserts the composable
> factories emit the right masks; the ALU flag-truth-table tests (Task 5) assert the inline exprs.

### D.2 The class/mode matrix — "substantially rebuilt, not extended" (ADR `0001-…:377`)

The current matrix (`SpecParser.ClassifyOps` `:664-781`, `ValidateModeForClass` `:791-854`,
`RequiredIndexRegister` `:784-789`) encodes 6502 rules. The Z80 base plane breaks several:

| 6502 rule (file:line) | How the Z80 base plane breaks it | M3.4a change |
|---|---|---|
| `RequiredIndexRegister` — "X-indexed mode needs a reg named X" (`:784-789`) | meaningless for the Z80; no base-plane mode needs it | the NEW modes return `null` from `RequiredIndexRegister` (they require no index register) — additive, the 6502 `ZeroPageX`→`X` mapping is untouched |
| `ValidateModeForClass` — register class is `Implied` ONLY (`:796-798`) | Z80 register-class ops are `Register` mode (`LD r,r'`, `OR r`) | add `Register`/`RegisterIndirect` to the register/ALU/load/store classes' legal modes |
| Jump class is `Absolute`/`Indirect` only (`:821-823`) | Z80 `JP cc,nn` (conditional jump), `JP (HL)` (`RegisterIndirect`), `JR`/`JR cc` (`RelativeJump`) | a NEW conditional-flow class (Z80 conditionally CALLs/RETs/JPs — `0001-…:364-366`) + `RegisterIndirect` for `JP (HL)` |
| Branch class is `Relative` only, ONE `BranchIf` op (`:826-828`) | Z80 has `JR cc,d` (relative + condition) AND `DJNZ` (relative + B-decrement-and-test) | a `RelativeJump`-mode flow class with the new `RelJump`/`RelJumpIf`/`Djnz` ops |
| Stack class is `Implied`, 8-bit `Push`/`Pull` (`:831-833`, `:739-747`) | Z80 `PUSH BC`/`POP BC` push a 16-bit PAIR | the new `Push16`/`Pop16` ops in `Register` mode (the pair-name is the operand) |
| flow class is `Jsr`/`Rts`/`Brk`/`Rti`, fixed modes (`:837-844`) | Z80 `CALL cc,nn`, `RET cc`, `RST n` | the conditional-flow class + `Rst(vec)` + `CallIf`/`RetCc` |

**The cleanest model: a new `InstructionClass` set the Z80 base plane needs**, classified by
`ClassifyOps` from the first op's kind, with `ValidateModeForClass` extended per new class. The
parser change is the largest single mechanical edit in M3.4a (ADR predicted this). The 6502 classes
(`Register`/`Load`/`Store`/`Jump`/`Branch`/`Alu`/`Rmw`/`Stack`/`Flow`/`Port`) and their mode rules are
**untouched** (additive) — the Z80 adds classes/modes alongside them.

> **Recorded judgement call: extend the matrix vs. rebuild it.** ADR says "substantially rebuilt"
> (`:377`). The HONEST middle path M3.4a takes: the 6502 classes' rules stay byte-identical (additive
> proof); the Z80's new shapes (conditional CALL/RET/JP, the relative-jump family, the 16-bit pair
> stack, the `Register`/`RegisterIndirect` modes across load/ALU) are added as NEW classes + NEW
> mode-legality entries. Whether this reads as "extend" or "rebuild" is academic — the test is that
> the 6502 matrix entries are unchanged (pinned) AND every M3.4a base-plane row classifies + validates
> (pinned by the regenerated-spec-compiles gate, Task 7). If a base-plane row resists the matrix (a
> shape neither extend nor a clean new class fits), that is a Task-finding — surface it.

### E.1 The 8-bit ALU (flag-correct Z80 — the bulk of the flag work)

The 6502 `Adc`/`Sbc`/`And`/`Ora`/`Eor`/`Compare` factories set the 6502 N/Z/C/V convention — WRONG
for the Z80 (`m3d-…:564-570`). M3.4a adds Z80-flag-correct ops (suffixed `8` to coexist):

| Z80 op | Factory | Modes | C | Z | P/V | S | H | N | X/Y |
|---|---|---|---|---|---|---|---|---|---|
| `ADD A,s` | `Add8()` | Register, RegisterIndirect, Immediate | carry-out | res==0 | signed overflow | res bit7 | carry bit3→4 | 0 | res bit3/5 |
| `ADC A,s` | `Adc8()` | (same) | carry-out incl old C | res==0 | overflow | res bit7 | half-carry incl C | 0 | res bit3/5 |
| `SUB s` | `Sub8()` | (same) | borrow | res==0 | overflow | res bit7 | half-borrow | 1 | res bit3/5 |
| `SBC A,s` | `Sbc8()` | (same) | borrow incl old C | res==0 | overflow | res bit7 | half-borrow incl C | 1 | res bit3/5 |
| `AND s` | `And8()` | (same) | 0 | res==0 | **parity** | res bit7 | **1** | 0 | res bit3/5 |
| `OR s` | `Or8()` | (same) | 0 | res==0 | **parity** | res bit7 | **0** | 0 | res bit3/5 |
| `XOR s` | `Xor8()` | (same) | 0 | res==0 | **parity** | res bit7 | **0** | 0 | res bit3/5 |
| `CP s` | `Cp8()` | (same) | borrow | res==0 | overflow | res bit7 | half-borrow | 1 | **operand** bit3/5 (CP's quirk: X/Y from the OPERAND, not the result) |

The accumulator is always `A` (the Z80 8-bit ALU is A-centric); the SOURCE `s` is a register
(`Register` mode), `(HL)` (`RegisterIndirect`), or `n` (`Immediate`). A representative emitter body
(`ADD A,r`) is given as literal code in Task 5. **The `CP` X/Y-from-operand quirk** is a TomHarte-
checked subtlety — recorded so the implementer does not copy the result-bit pattern.

### E.2 INC/DEC (8-bit) — H and overflow, C PRESERVED

`INC r` / `DEC r` (`Register`, and `INC (HL)`/`DEC (HL)` `RegisterIndirect`): factories `IncReg("B")`/
`DecReg("B")` (8-bit) and the memory forms reuse `RegisterIndirect`. Flag rules: S/Z/X/Y from result;
H = (INC: bit3 carry; DEC: bit3 borrow); P/V = overflow (set iff INC from 0x7F or DEC from 0x80);
N = 0 (INC) / 1 (DEC); **C is PRESERVED** (the Z80 INC/DEC do NOT touch carry — distinct from the ALU
ops and from any 6502 op). Recorded as a flag-rule the emitter must NOT set C.

### E.3 16-bit ALU

- `ADD HL,rr` → `Add16("HL","BC"|"DE"|"HL"|"SP")` (opcodes 0x09/0x19/0x29/0x39). Flags: C = carry out
  of bit 15; H = carry out of bit 11; N = 0; X/Y = bits 13/11... (actually bits 5/3 of the HIGH byte
  of the result); **S/Z/P-V are PRESERVED** (a Z80 quirk). Recorded.
- `INC rr` / `DEC rr` → `Inc16("BC")` / `Dec16("BC")` (operate on the pair view). **Set NO flags** —
  the ADR-flagged quirk (`0001-…:347`): the generator must NOT add SetSZ "helpfully."

### E.4 LD forms (the matrix)

| Z80 form | Mode | Factory mapping | New op? |
|---|---|---|---|
| `LD r,r'` | Register | `[Transfer("dst","src")]` | reuses 6502 `Transfer` (8-bit) |
| `LD r,n` | Immediate | `[Load("dst")]` over Immediate | reuses `Load` (but over a register target — the EA is the register) |
| `LD r,(HL)` / `LD (HL),r` | RegisterIndirect | `[Load("r")]` / `[Store("r")]` over the pair-EA | reuses `Load`/`Store`, NEW mode |
| `LD (HL),n` | RegisterIndirect + Immediate | a store-immediate-to-(HL) | a small new arm (immediate → pair-EA) |
| `LD A,(BC)` / `LD A,(DE)` / `LD (BC),A` / `LD (DE),A` | RegisterIndirect | `[Load("A")]` / `[Store("A")]` over (BC)/(DE) | reuses `Load`/`Store`, NEW mode |
| `LD rr,nn` | ImmediateExtended | `Load16("rr")` | NEW `Load16` (16-bit immediate → pair/16-bit reg) |
| `LD (nn),HL` / `LD HL,(nn)` | ExtendedAddress | `Store16("HL")` / `Load16From("HL")` | NEW 16-bit `(nn)` word access |
| `LD (nn),A` / `LD A,(nn)` | ExtendedAddress | `Store("A")` / `Load("A")` over `(nn)` | reuses `Load`/`Store`, NEW mode (8-bit `(nn)`) |
| `LD SP,HL` | Register | a 16-bit register-to-register transfer | a 16-bit `Transfer` variant |

**None of the LD forms set flags** (the Z80 `LD` is flag-transparent — except `LD A,I`/`LD A,R` which
are ED-plane, M3.4b). Recorded.

### E.5 Pair PUSH/POP, EX/EXX

- `PUSH rr` / `POP rr` → `Push16("BC"|"DE"|"HL"|"AF")` / `Pop16(...)` (`Register` mode, the pair-name
  is the operand). 16-bit: push hi then lo, SP−2; pop lo then hi, SP+2. `POP AF` writes BOTH A and F
  (so it sets the flag word from the stack — the only POP that touches F).
- `EX DE,HL` → `ExDeHl()`: swap the DE and HL pair contents (swap D↔H, E↔L).
- `EX AF,AF'` → `ExAfAf()`: swap (A,F) with (A_,F_).
- `EXX` → `Exx()`: swap (B,C,D,E,H,L) with (B_,C_,D_,E_,H_,L_) wholesale (NOT AF).
- `EX (SP),HL` → `ExSpHl()`: exchange HL with the word at (SP) — a memory exchange (4 byte bus ops).

### E.6 Flow (conditional + unconditional)

| Z80 form | Mode | Factory | Notes |
|---|---|---|---|
| `JP nn` | ExtendedAddress | reuse `Jump()` | unconditional absolute |
| `JP cc,nn` | ExtendedAddress | `JumpIf(cc)` | cc ∈ {NZ,Z,NC,C,PO,PE,P,M} — 8 conditions over Z/C/P/S |
| `JP (HL)` | RegisterIndirect | a register-indirect jump (`Jump` over the pair-EA) | NOT a memory read — PC = HL directly |
| `JR d` | RelativeJump | `RelJump()` | PC += signed d |
| `JR cc,d` | RelativeJump | `RelJumpIf(cc)` | cc ∈ {NZ,Z,NC,C} (JR only has 4) |
| `DJNZ d` | RelativeJump | `Djnz()` | B−−; if B≠0 PC += d (uses register B) |
| `CALL nn` | ExtendedAddress | reuse `Jsr()` | push PC, PC = nn |
| `CALL cc,nn` | ExtendedAddress | `CallIf(cc)` | conditional call (8 conditions) |
| `RET` | Implied | reuse `Rts()` | pop PC |
| `RET cc` | Implied | `RetCc(cc)` | conditional return (8 conditions) |
| `RST n` | Implied | `Rst(vec)` | push PC, PC = vec (vec ∈ {0x00,0x08,…,0x38}) |

**The condition-code (cc) operand.** The 8 Z80 conditions test Z/C/P-V/S flags (NZ/Z/NC/C/PO/PE/P/M).
The `JumpIf`/`CallIf`/`RetCc`/`RelJumpIf` factories carry a `cc` argument — modeled as a `Flag` +
sense pair (like the existing `BranchIf(Flag, bool)`, `Op.cs:14`) so `JP NZ,nn` = `JumpIf(Flag.Z,
false)`. The 4 JR conditions are a subset; the parser validates the cc against the op (`JR` rejects
P/S conditions — a Task-finding if the dataset encodes them). The conditional taken/not-taken **cycle
difference** (the Z80's variable timing) is handled in the emitter's cycle accounting (Ground truth G).

### E.7 Misc

- `DAA` → `Daa()`: BCD-correct `A` after an add/sub, using H and N (NOT a `D`-flag like the 6502 — the
  Z80 has no decimal-mode flag, ADR J7 `0001-…:511`). Sets S/Z/X/Y/P(parity)/C/H. The correction table
  is the documented Z80 DAA algorithm (a representative arm in Task 5's notes; the truth is the
  TomHarte 0x27 vectors).
- `CPL` → `Cpl()`: A = ~A; sets H=1, N=1; X/Y from the new A; preserves S/Z/P/C.
- `SCF` → `Scf()`: C=1, H=0, N=0; X/Y from A (the SCF/CCF X/Y-from-A quirk TomHarte's `q` tracks).
- `CCF` → `Ccf()`: C = ~C, H = old C, N=0; X/Y from A.
- `DI`/`EI` → `Di()`/`Ei()`: clear/set IFF1+IFF2. These need IFF1/IFF2 STATE in the partial (Ground
  truth F) and are observable in the TomHarte final state's `iff1`/`iff2`. `EI`'s one-instruction
  enable-delay (ADR `0001-…:428`) is NOT exercised by single-instruction TomHarte vectors (the vector
  ends after one Step), so M3.4a sets the latch and records the delay as an M3.4b interrupt-servicing
  concern.
- `NOP` (0x00) and `HALT` (0x76) are already covered (`Z80Spec.cs:54,172`).

### E.8 The semantics-map authoring + the FactoryArity additions

`z80-semantics.json` `mnemonics` grows from 13 entries to cover all 31 base-plane mnemonics (the
`ADD`/`ADC`/… ALU entries SWITCH from the 6502 `Adc()`/`Sbc()`/… to the Z80 `Add8()`/`Adc8()`/…;
`ADD` splits into `Add8`/`Add16` by operand — Ground truth A's conflation note). `SemanticsMap.
FactoryArity` (`:44-90`) gains the new factory names + arities. **No 6502 factory is removed** — the
6502 keeps `Adc`/`Sbc`/… ; the Z80 adds `Add8`/`Adc8`/… alongside. (Recorded: the suffix-`8` naming
avoids a collision; the 8086 8/16-bit ALU will reuse `Add8`/`Add16`, so the names are forward-general.)

## Ground truth G — the cycle-accuracy bar: per-T-state bus-trace fidelity

**The decision (ADR risk #5, `0001-…:704-707`): M3.4a holds the Z80 interpreter to per-T-state
bus-trace fidelity — TomHarte's bar.** The TomHarte Z80 `cycles` array samples the bus per T-state
(with `m`/`i` request signals and `r`/`w` direction), so passing the vectors REQUIRES the interpreter
to produce the right bus transactions in the right T-state order. This is the same bar the 6502
interpreter meets (`Mos6502TomHarteTests` diffs the bus trace, `TomHarteRunner.cs:55-65`).

**What this means concretely:**
- The Z80 `cycles` field in the M3.3 dataset is the **total T-state count** (`m3d-…:290`). The emitter
  charges cycles to match the T-state total AND emits bus accesses in the documented T-state order.
- The Z80's timing is NOT "one cycle = one bus access" (the 6502 model, ADR J5 `0001-…:509`): a Z80
  instruction has M-cycles (3–6 T-states each) with internal (non-bus) T-states. So `_cycles` is bumped
  for internal T-states too, NOT only on `ReadBus`/`WriteBus`. **The emitter's cycle accounting for the
  Z80 charges the descriptor's T-state total, distributing bus accesses at their documented T-states**
  — a per-class cycle template like the 6502's `ComputeCycles` (`CpuEmitter.cs:302+`) but with Z80
  values. The conditional ops (`JR cc`, `CALL cc`, `RET cc`, `DJNZ`) have taken/not-taken T-state
  counts; the dataset records the not-taken base (`m3d-…:303-306`) and the emitter adds the taken
  penalty (parallel to the 6502 branch +1).
- The bus-trace diff in the runner compares `(address, value, isRead, signal)` per T-state. The Z80
  trace has T-states with NO bus access (internal) — represented in the TomHarte data as entries with
  null address/value (the "electrically disconnected" states, Ground truth H). The runner must handle
  null-bus T-states (the 6502 trace has none).

> **The honest risk: per-T-state Z80 bus ordering is the hardest part of the base-plane gate.** Getting
> the registers + flags right is well-specified (Ground truth E's tables). Getting the per-T-state bus
> trace right — the internal T-states, the M-cycle boundaries, the exact order of operand-byte fetches
> vs. the write-back — is where a base-plane op most likely diverges from TomHarte. **Mitigation (the
> staged gate):** the runner runs the register+memory diff FIRST and the bus-trace diff SECOND, with a
> mode to assert registers-only initially (so flag/register correctness is provable before the
> full-trace bar). A base-plane op that is register/flag-correct but bus-trace-divergent is a known,
> bounded fix (the T-state distribution), not a correctness bug. Recorded as the gate's two-stage
> structure (Task 8); the FULL gate (incl. bus trace) is the M3.4a exit criterion.

## Ground truth H — the Z80 TomHarte harness + the covered base-plane set

### H.1 Vector availability — CONFIRMED, but a DIFFERENT repo from the 6502

**The Z80 SingleStepTests vectors EXIST and are confirmed available** at
**`https://github.com/SingleStepTests/z80`** — a SEPARATE repository from the 6502's
`SingleStepTests/ProcessorTests` (which the existing `get-test-vectors.ps1:13-16` clones). Key facts
verified against the repo:

- **Structure:** a `v1/` directory, one JSON file per opcode encoding, **1000 cases per file** (the
  6502 has 10,000; the Z80 files are smaller).
- **The JSON schema DIFFERS from the 6502's** (`TomHarteCase.cs:10-19` documents the 6502 shape):
  - Registers in `initial`/`final`: `a b c d e f h l ix iy sp pc` (8/16-bit), the alternate set as
    PACKED 16-bit pairs `af_ bc_ de_ hl_`, and the specials `i r wz` + `iff1 iff2 im` + `p` (tracks
    `LD A,I/R`) + **`q`** (tracks whether flags were modified last — drives the SCF/CCF X/Y quirk).
  - `ram`: `[address, value]` pairs (same as 6502).
  - `cycles`: `[address, data, signal_string]` where the signal codes are `r`(read) `w`(write)
    `m`(memory request) `i`(I/O request); **null** address/value = an electrically-disconnected
    (internal) T-state.
  - **`ports`:** a SEPARATE array `[16-bit_address, value, "r"/"w"]` for I/O transactions (the 6502 has
    no separate port array — I/O is memory-mapped there). The base plane's `IN A,(n)`/`OUT (n),A` use
    it.

**The harness must therefore add a Z80-specific loader** (the shape is different enough that reusing
`TomHarteLoader` is wrong) and a **Z80 variant of `get-test-vectors`** that clones the `z80` repo into
a `z80/v1` cache dir. **This is a load-bearing finding** — flagged prominently, not buried: the brief
asked "whether the Z80 vectors are actually available (which repo/URL — flag if uncertain, with a
skip-when-absent harness like Klaus)." **Answer: AVAILABLE at `SingleStepTests/z80` (v1, 1000
cases/file), with a distinct JSON schema. The harness uses the SAME skip-when-absent discipline as the
6502 (`TomHarteVectors.cs:30-38`) so the suite stays green when vectors are absent.**

> **A residual uncertainty to verify at Task 0/6 (not assumed):** the EXACT cache-dir layout and
> whether the `z80` repo supports the same sparse-checkout `--filter=blob:none --sparse` flow as
> `ProcessorTests`. The 6502 script sparse-checkouts `6502/v1`; the Z80 repo's top-level IS the test
> set (no per-CPU sub-dir), so the Z80 script clones `v1/` directly. The implementer CONFIRMS the
> clone flow against the live repo at Task 6 and records the exact URL/flow — if the repo layout
> differs from this plan's read, that is a recorded adjustment, not a blocker (the vectors exist; only
> the fetch mechanics are confirmed at implementation time).

> **Recorded deviation: the Z80 base-plane semantics are derived ALGORITHMICALLY from the opcode byte**
> (`tools/.../Z80BaseSemantics.cs`), not from a per-mnemonic `mnemonics` map. The dataset carries NO
> operand field, and the same mnemonic (LD/ADD/INC/DEC) maps to many distinct ops by the register/pair
> the opcode bits select — a per-mnemonic map cannot express that. The regular Z80 octal encoding
> (`xx yyy zzz`) makes the per-opcode operand resolution exact. The per-mnemonic `z80-semantics.json`
> map shrank to NOP/HALT/NEG (the ED NEG still rides the map). `JP nn`/`CALL nn`/`RET` use dedicated
> Z80 ops (JumpAbs/CallAbs/Ret), not the reused 6502 Jump/Jsr/Rts, because the Z80 16-bit stack layout
> differs from the 6502's 0x100+SP convention.
