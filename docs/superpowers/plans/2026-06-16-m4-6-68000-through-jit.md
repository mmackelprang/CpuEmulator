# M4.6 — the 68000 through the JIT (all-fallback tier parity, data axis)

> **For agentic workers:** REQUIRED SUB-SKILL — use `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> This is a PLUMBING PR, not a JIT re-architecture: the generic JIT seam was already built and proven by the Z80
> (M3.5-3a, PR #31) and the generator ALREADY emits a `GeneratedJitTarget` for the 68000. M4.6 closes the three
> small wiring gaps that remain, then proves byte-identical Tier-0-vs-Tier-1 parity on the DATA axis with the same
> per-case runner the data-axis sweeps already use.

**Goal.** Wire the complete, functionally-finished 68000 interpreter (`M68000Cpu`, M4.5a–d-1 merged) through the
generic `JittedCpu<M68000Cpu>` as **all-fallback**, and prove **byte-identical Tier-0 (interpreter) vs Tier-1 (JIT)
parity on the data axis** — the same parity gate the Z80 uses (the Z80 went through the generic seam with ZERO
JIT-assembly change; M4.6 follows that template exactly). Per ADR 0008 §6, **M4.6 depends only on M4.5d-1 (merged,
PR #43), NOT on M4.5d-2** (the timing/prefetch axis): the JIT parity gate is the DATA axis, and the synchronous
mid-instruction vector (TRAP / ÷0 / address-error) is handled by the fallback valve — an exception-capable op bails
to the interpreter, which owns the vector machinery.

**Architecture (the load-bearing fact).** The 68000 is **all-fallback** in M4 (ADR 0003 Decision 3, ADR 0004 §2
Decision 3 — exception-capable ops are `NeedsFallback` first; and in M4 NO 68000 op emits IL at all). The generated
`M68000Cpu.JitTarget` already exists, and `M68000Cpu.JitDescriptorsByKey` is **empty `{}`** — so
`M68000Cpu.DescriptorFor(key)` ALWAYS returns `OpcodeDescriptor.Undefined`, which is
`NeedsFallback: true, EndsBlock: true, Class: Undefined`. That means every discovered 68000 block contains exactly
ONE op, that op emits an `inner.Step()` callout (`EmitFallbackStep` — short-circuited at `BlockCompiler.cs:209`
BEFORE the `EmitInstruction` class switch, so the `Undefined` class never hits the `default` throw), and the block
ends. **A 68000 JIT block IS the interpreter, one instruction at a time** — so a green tier-parity sweep proves the
generic compiler (the discovery walk, the keyed `DescriptorFor`, the per-CPU `BlockDelegate`, the data-driven
register map, the cycle/budget/dispatch machinery) drives the 68000 faithfully, exactly as 5-3a proved it for the
Z80. **No `BlockCompiler.Emit.cs`/`Flow.cs`/`Decimal.cs` arm is reached; no Z80/6502 emit logic changes.**

**Tech Stack:** C# .NET 10, `System.Reflection.Emit` (already generic over `TCpu` since 5-3a), the Roslyn source
generator (`CpuEmulator.Generators`), `CpuEmulator.Jit`, xUnit + the SingleStepTests/680x0 v1 gzip vectors
(`M68000TomHarteLoader` / `M68000TomHarteRunner`, M4.4b–M4.5d-1).

## The PURE-PLUMBING-vs-JIT-CHANGE question (resolved here; surfaced in the Decisions block)

ADR 0008 §6 predicts M4.6 "wraps the CPU in `JittedCpu<M68000Cpu>` ... since the 68000 is all-fallback ... the
fallback valve handles the synchronous vector ... M4.6 needs the functional exception model (M4.5d-1) but is
agnostic to the prefetch/timing axis." The M4-status doc predicts "zero JIT-assembly change per the M3.5-3c
findings; the generic seam is ready." Both are CORRECT for the EMIT path. The one place the prediction meets a real
24-bit detail is GAP 3 (R6) + R7: the **dispatcher's cache key and discovery fetch stream are `ushort`/byte-granular**,
baked when the only two CPUs were 16-bit-PC (6502, Z80).

**Why it is still effectively pure plumbing for the M4.6 GATE.** The M4.6 parity gate runs ONE instruction per case
through a FRESH `JittedCpu<M68000Cpu>` (the runner builds a new CPU + bus per case, R8). In that single Step:
- `Run(ref budget)` calls `GetOrCompile((ushort)PC)` once, compiles ONE block (one fallback op), runs it; the
  fallback `inner.Step()` advances the **real 24-bit PC** on the interpreter; the block ends; budget drives one
  iteration. The `(ushort)PC` truncation only affects the cache KEY, and the cache holds at most one block for the
  one case — **no aliasing is possible within a single-instruction case.** The DATA-axis result (regs/SR/RAM) is
  produced entirely by `inner.Step()`, which is byte-identical to Tier-0 by construction.
- `Discover` builds `new BusFetchStream(_bus, pc)` and calls `_target.Decode(stream)`. For the 68000, `Decode`
  reads `stream.NextUnit()` expecting 16-bit big-endian WORDS, but `BusFetchStream` returns single BYTES (R7). The
  resulting `OperationKey` is therefore "wrong" — BUT it does not matter: `DescriptorFor(anyKey)` returns
  `Undefined` (R3) regardless of the key (the table is empty), so the descriptor is `NeedsFallback`/`EndsBlock`
  either way. The discovered block is `[(pc, Undefined, len)]` and emits one fallback. **The mis-fetch is inert
  in all-fallback mode** because the key is never used to select a real (non-fallback) descriptor.

So the **minimal M4.6 (Decision A → "pure plumbing")** ships GAP 1 + GAP 2 + the runner + the sweep, and documents
the `ushort`-key / byte-fetch dispatcher as a **known all-fallback-safe limitation** with a guard test pinning the
single-instruction-per-block invariant. This is the honest, lowest-risk path and matches the ADR/status prediction
verbatim ("zero JIT-assembly change").

**The alternative (Decision A → "widen now").** Widen the dispatcher's PC key from `ushort` to `uint`
(`JittedCpu.Run`, `BlockCache`, `Discover`/`Compile`/`CompiledBlock`/`ResolveChain`) and make `Discover` build the
per-CPU fetch stream via a new `IJitTarget.NewFetchStream(bus, pc)` seam (so the 68000 gets `M68000FetchStream`,
the 6502/Z80 get `BusFetchStream`). This removes the latent multi-instruction-`Run` aliasing/mis-fetch for a 24-bit
PC — but it is a genuine JIT-assembly change touching the shared dispatcher, with a 6502/Z80 byte-identity
regression surface, and it is NOT required for the M4.6 data-axis gate (all-fallback never exercises the bug).

**Recommendation: Decision A = pure plumbing (minimal), with the limitation documented + a guard test.** Defer the
`uint`-key + per-CPU-fetch-stream widening to the post-M5 cross-arch JIT-optimization phase (M6), where the 68000's
hot ops are first emitted as IL — at THAT point a 68000 block can statically continue past one instruction, the
24-bit PC arithmetic in `EmitChainOrExit`/`EmitBudgetCheck` (`Conv_U2`) becomes live, and the widening is
load-bearing and reviewed alongside the emit work it actually enables. Until then the 68000 JIT is correct (all-
fallback tier parity) and the widening buys nothing the gate can prove. **Surfaced as Decision A for the owner.**

```csharp
// add to tests/CpuEmulator.Tests/TomHarte/M68000TomHarteRunner.cs (mirrors RunCase; Tier-1 path)
/// <summary>M4.6 tier-parity path: run one case through JittedCpu&lt;M68000Cpu&gt; (all-fallback) and diff
/// the DATA axis against the case's final state — the byte-identical Tier-0-vs-Tier-1 gate. Mirrors
/// RunCase exactly except it drives Run(ref budget) (a one-instruction budget) instead of Step(). The
/// budget is the case length so the single fallback op completes; the JIT's block-entry interrupt check
/// + the fallback valve handle the synchronous mid-instruction vector (TRAP/÷0/privilege) authentically
/// (the exception-capable op bails to inner.Step). Returns null on pass / DeferredException for deferred /
/// a formatted report on failure — the same contract as RunCase.</summary>
public static string? RunCaseThroughJit(M68000TomHarteCase c, bool assertExceptions = false)
{
    if (!assertExceptions && IsExceptionCase(c)) return DeferredException;
    if (assertExceptions && IsAddressErrorCase(c)) return DeferredException;   // DD4: vector-3 stays deferred

    var inner = new AddressSpace(AddressSpaceKind.Program, addressBits: 24,
        endianness: Endianness.BigEndian);
    inner.MapMemory(0x000000, new byte[0x1000000], writable: true);
    foreach (var e in c.Initial.Ram) inner.Write8(e.Address & inner.AddressMask, e.Value);

    uint pc = c.Initial.Pc;
    ushort[] pf = c.Initial.Prefetch;
    if (pf.Length > 0) inner.Write16((pc + 0u) & inner.AddressMask, pf[0]);
    if (pf.Length > 1) inner.Write16((pc + 2u) & inner.AddressMask, pf[1]);

    // JIT fastmem binds to the concrete AddressSpace (no TracingAddressSpace — the JIT data-axis gate
    // asserts regs/SR/RAM, NOT the per-transaction trace; trace-equivalence is the interpreter axis).
    var (jit, cpu) = M68000JittedCpuFactory.Create(inner);
    var s = c.Initial;
    for (int i = 0; i < 8; i++) cpu.SetRegister($"D{i}", s.D[i]);
    for (int i = 0; i < 7; i++) cpu.SetRegister($"A{i}", s.A[i]);
    cpu.SetRegister("USP", s.Usp);
    cpu.SetRegister("SSP", s.Ssp);
    cpu.SetRegister("PC", s.Pc);
    cpu.SetRegister("SR", s.Sr);

    // One instruction through Tier-1. The budget is the case's cycle length so the single fallback op
    // (which charges its real cycles via inner.Step) completes within one Run iteration; overshoot is
    // bounded by one instruction (JittedCpu.Run exits at the block boundary). A floor keeps a zero-length
    // edge case from no-op'ing the Run loop.
    long budget = System.Math.Max(c.Length, 1);
    jit.Run(ref budget);

    var problems = new System.Collections.Generic.List<string>();
    void Check(string name, uint expected)
    {
        uint got = (uint)cpu.GetRegister(name);
        if (got != expected) problems.Add($"{name}: expected {expected:X8}, got {got:X8}");
    }
    var f = c.Final;
    for (int i = 0; i < 8; i++) Check($"D{i}", f.D[i]);
    for (int i = 0; i < 7; i++) Check($"A{i}", f.A[i]);
    Check("USP", f.Usp);
    Check("SSP", f.Ssp);
    { uint gotSr = (uint)cpu.GetRegister("SR"); if (gotSr != f.Sr) problems.Add($"SR: expected {f.Sr:X4}, got {gotSr:X4}"); }
    foreach (var e in f.Ram)
        if (inner.Read8(e.Address & inner.AddressMask) != e.Value)
            problems.Add($"RAM[{e.Address:X6}]: expected {e.Value:X2}, got {inner.Read8(e.Address & inner.AddressMask):X2}");

    return problems.Count == 0 ? null : Format(c, problems);
}
```

## Decisions for Coordinator/user review

> Stated with recommendation, alternative, and risk. **A** is the load-bearing one (it decides pure-plumbing vs.
> a bounded JIT change). **B/C/D** are scope confirmations.

**A. Is M4.6 PURE PLUMBING (the recommended minimal path), or does it also WIDEN the dispatcher's PC key + fetch
stream to 24-bit now?**
- *Finding (verified):* the generic JIT seam is ready and the 68000 `JitTarget` is already generated; the only
  production work is GAP 1 (`AdvanceCycles`) + GAP 2 (`InternalsVisibleTo`) — both hand-written, ~3 lines, mirroring
  `Z80Cpu.Jit.cs`. The 68000 is all-fallback (empty `JitDescriptorsByKey` → every op `Undefined`/`NeedsFallback`),
  so **NO `BlockCompiler` emit arm, no IL, no JIT-assembly logic changes** — matching the ADR 0008 §6 + M4-status
  prediction "zero JIT-assembly change." GAP 3 (R6/R7) — the dispatcher casts the 24-bit PC to `ushort` for the
  cache key and uses a byte-granular `BusFetchStream` in `Discover` — is a real latent issue but is **inert in
  all-fallback mode**: the cache key only aliases across MULTIPLE instructions in one `Run`, and the M4.6 gate runs
  ONE instruction per fresh CPU; the mis-fetched decode key is discarded because the empty table routes every key
  to `Undefined`. The fallback `inner.Step()` sets the real 24-bit PC.
- *Recommendation:* **PURE PLUMBING (minimal path).** Ship GAP 1 + GAP 2 + the parity runner + the family sweep;
  DOCUMENT the `ushort`-key/byte-fetch dispatcher as a known all-fallback-safe limitation; PIN the single-block
  invariant with the GAP-3 guard test (Task 2). **Defer the `uint`-key + per-CPU `IJitTarget.NewFetchStream`
  widening to M6** (the cross-arch JIT-optimization phase), where the 68000's hot ops are first emitted as IL — at
  which point a 68000 block can statically continue past one instruction, the 24-bit PC arithmetic in
  `EmitChainOrExit`/`EmitBudgetCheck` (`Conv_U2`) goes live, and the widening is load-bearing and reviewed
  alongside the emit work it enables.
- *Alternative:* widen the PC key to `uint` + add the per-CPU fetch-stream seam in M4.6. Buys correctness the M4.6
  gate cannot exercise (all-fallback never hits the bug), at the cost of a shared-dispatcher change with a 6502/Z80
  byte-identity regression surface — premature per YAGNI and the "build the emitter once for all 3 ISAs" M6 thesis.
- *Risk:* minimal path = **LOW** (additive partials + tests; the dispatcher is untouched). Widen-now = **MEDIUM**
  (shared dispatcher edit; 6502/Z80 parity must be re-proven).
- *Tripwire (Task 2 Step 2):* if the byte-granular `BusFetchStream` makes `M68000Cpu.Decode` THROW (rather than
  produce an ignored key), the minimal path is insufficient and A flips to a SCOPED widen — only the
  `IJitTarget.NewFetchStream` seam (so `Discover` builds `M68000FetchStream`), NOT the full `uint`-key change. The
  recon predicts no throw (unmatched operword → no field-op match → `Undefined`), but the tripwire makes it
  falsifiable.

**B. The parity-gate SCOPE: data axis only (the recommended gate), with the timing axis gated on M4.5d-2.**
- *Recommendation:* **Data axis only** (D0–D7/A0–A6/USP/SSP/SR/RAM, byte-exact), the same Tier-1 scope the 6502 +
  Z80 JIT sweeps assert (fastmem bypasses the per-transaction trace — Ground truth E). This mirrors the interpreter
  data-axis discipline M4.5a–d-1 used and is exactly what ADR 0008 §6 scopes M4.6 to ("the JIT parity gate is the
  data axis").
- *Alternative:* assert the timing axis (final.pc/prefetch/trace/cycle) through the JIT too. **Rejected for M4.6** —
  the timing axis requires the prefetch-queue model, which is M4.5d-2 (HELD for the owner, seam-breaking). The JIT
  cannot assert timing the interpreter does not yet produce. When M4.5d-2 lands, a follow-on can flip `timingAxis`
  on in `RunCaseThroughJit` (the branch is already structured for it).
- *Risk:* **LOW.** The data-axis gate is complete and self-contained; the timing axis is a clean future extension.

**C. The `NeedsFallback` coverage approach: rely on the EMPTY descriptor table (every op `Undefined` →
`NeedsFallback`), NOT a per-op `NeedsFallback` audit.**
- *Finding:* the 68000 emits NO descriptor rows (`JitDescriptorsByKey = {}`), so `DescriptorFor` returns
  `OpcodeDescriptor.Undefined` (`NeedsFallback:true, EndsBlock:true`) for EVERY key — the all-fallback property
  holds by construction, uniformly, for the ENTIRE ISA including the exception-capable ops (TRAP/CHK/÷0/privilege/
  address-error). There is no per-op marking to get wrong; the synchronous mid-instruction vector is handled by the
  fallback valve (the op bails to `inner.Step`, which owns the M4.5d-1 `RaiseException` machinery).
- *Recommendation:* **Rely on the empty-table all-fallback property; PIN it with a test** (Task 2:
  `FallbackEmitCount == 1` / single-`Undefined`-op-per-block), so a FUTURE PR that begins populating
  `JitDescriptorsByKey` (M6 hot-op emit) cannot silently flip an exception-capable op out of fallback without the
  pin failing. This is the honest, minimal, future-proof stance.
- *Alternative:* author explicit per-op `NeedsFallback:true` descriptor rows for the whole ISA now. **Rejected** —
  pure overhead (the empty table already yields universal fallback) and it would pre-build the descriptor scaffolding
  the M6 emit phase should own.
- *Risk:* **LOW.** The pin guards the one future-regression vector (M6 emit accidentally un-fallbacking an
  exception-capable op).

**D. The honesty carry-forwards M4.6 must NOT overclaim.**
- The IMMEDIATE forms (ADDI/SUBI/ANDI/ORI/EORI/CMPI) + QUICK forms (ADDQ/SUBQ) have NO dedicated v1 vector files
  (the M4.5b gap). The JIT sweep can only assert tier parity on files that EXIST — so their tier parity is
  TRANSITIVE (their vector-proven reg↔EA counterparts go through the identical fallback), NOT vector-green. **State
  this verbatim in the PR close-state (the M4.5b precedent).**
- The TIMING axis (final.pc/prefetch/trace/cycle) is NOT asserted through the JIT (gated on M4.5d-2) — same as the
  interpreter data-axis sweeps.
- The per-transaction bus TRACE is NOT asserted under fastmem (the same scope the 6502/Z80 JIT sweeps disclose).
- *Recommendation:* carry all three disclosures into the PR's honest close-state. *Risk:* **LOW** (disclosure, not
  behavior).
